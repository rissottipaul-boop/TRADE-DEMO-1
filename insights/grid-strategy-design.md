## 1. Когда grid применим (позиционирование)

Grid зарабатывает на осцилляциях цены внутри диапазона и структурно проигрывает в тренде: при устойчивом движении в одну сторону бот либо накапливает базовый актив на падении без шанса продать в прибыль, либо весь актив уходит в quote на росте, упуская продолжение [И1][И2]. Академическая работа по «zero-expectation» grid trading формально показывает, что в нейтральном (боковом) рынке матожидание сеточной торговли **до вычета издержек** близко к нулю (не отрицательно, не положительно) — то есть весь реальный edge стратегии — это устойчивое исполнение колебаний ниже уровня комиссий, а не прогноз направления [И3]. Отсюда прямое следствие для нашего дизайна: (а) вход в сетку обязан быть обусловлен подтверждённым боковым режимом, (б) любая экономика на комиссиях — не мелочь, а то, что превращает «около-нулевое» матожидание в отрицательное или положительное (см. §5.3).

**Гейт входа:** переиспользуем уже принятый в проекте классификатор режима из `.agents/skills/dca-bot-parameterizer/SKILL.md` (EMA20 + ATR%, тот же, что упомянут как «фильтр входа» в `grid-path.md` §1.4):
- `Range` (цена колеблется вокруг EMA20, нет устойчивого тренда, ATR% в пределах обычного) → **вход разрешён**.
- `Strong Trend` / `Mild Trend` → **вход запрещён**, существующая сетка — под повышенным вниманием (см. §4.2 «зона предупреждения»).

Источники: [И1] Bitsgap, «Grid Trading Strategy Crypto: How Grid Bots Work» (2026) — грид эффективен в боковике, уязвим на пробое диапазона; [И2] Pionex, «Grid Trading Risks | When Grid Bots Lose Money» — то же наблюдение с независимой площадки; [И3] arXiv:2506.11921, «Dynamic Grid Trading Strategy: From Zero Expectation to Market Outperformance» (2025) — формальный анализ нулевого матожидания в нейтральном рынке до издержек.

## 2. Диапазон: ширина и режим

Переиспользуем методику, уже валидированную и обкатанную на нативном боте проекта (`grid-path.md` §1.4, применено в `grid-bot-demo-run.md`):

- Ширина диапазона `range_pct = (maxPx − minPx) / minPx × 100` — коридор **5–15%** вокруг текущей цены.
- Волатильность определяет **ширину диапазона** (не шаг — см. поправку §5.3):
  - BB bandwidth (4H) `> 8%` (высокая) → ширина 12–15%;
  - `4–8%` (обычная) → ширина 8–12%;
  - `< 4%` (низкая) → ширина 5–8%.
- Диапазон центрируется вокруг текущей цены; если 50-баровое окно (4H) даёт ширину `> 15%` (как было при запуске нативного бота — `grid-bot-demo-run.md` §2, факт 16.6%), диапазон сознательно сужается до целевого коридора, а не берётся «как есть».
- Перед созданием — обязательная сверка с `GET /tradingBot/grid/ai-param` (REST, публичный, работает в demo — подтверждено `grid-bot-demo-run.md` §3): расхождение `minPx`/`maxPx` с AI OKX `> 20%` фиксируется как метрика (не блокер), это часть критерия «своя сетка нужна» из `grid-path.md` §4 п.4.

## 3. Правило остановки всей сетки при выходе из диапазона

Это центральное требование roadmap (Фаза 2, п.3) и главное отличие от простого использования нативного бота (у нативного бота выход из диапазона = «заморозка», обслуживается вручную надзором — `grid-path.md` §2).

### 3.1 Триггер (hard stop)

- **В backtest** (свечные данные): стоп срабатывает на первом подтверждённом баре working-таймфрейма, где `low < minPx` или `high > maxPx`, проверяется в порядке **«low раньше high»** — то же консервативное допущение, что уже принято для стоп-ордеров в `backtester-design.md` §1.1.7 (переиспользуем правило движка бэктестера, не изобретаем новое). Исполнение — по цене границы (`minPx`/`maxPx`), к которой применяется проскальзывание §5.2.
- **В live/demo** (тиковые данные): решение принимается по **mid-цене** публичного стакана (не по `last`/тикеру — по эмпирическому выводу `demo-slippage.md` §5: демо-тикер шумнее live mid), с подтверждением устойчивости **≥30 секунд** (`breakout_confirm_seconds`, конфигурируемо) — чтобы не реагировать на одиночный фитиль/всплеск. Немедленный (без задержки) триггер — если цена ушла за границу больше чем на **1 дополнительный шаг сетки** (защита от гэпа/флэш-краха, где 30-секундное ожидание само по себе рискованно).
  - Аналогия в контракте OKX: у `triggerParams[].triggerStrategy=price` есть параметр `delaySeconds` именно для этого — задержка подтверждения перед срабатыванием триггера всей сетки (`spot-strategies.md`, открытый вопрос №1, закрыт 2026-09-24) [И-вн-1]. Внешние площадки решают ту же проблему через «Pump Protection»/сглаживание триггера (Bitsgap) [И4] — независимое подтверждение практики.

### 3.2 Действие при срабатывании (последовательность, атомарно с точки зрения журнала)

1. Отмена **всех** активных ордеров уровней сетки (и buy, и sell) — по аналогии с обязательной очисткой `orders-algo-pending` при kill-switch (`risk-core.md` §4).
2. Рыночная ликвидация остатка базового актива в quote-валюту — эквивалент нативного `stopType=1` («продать базу обратно»). Это осознанный выбор дефолта **именно для grid** (не путать с общим открытым вопросом `KILL-FLATTEN-DEFAULT` про дефолт системного kill-switch — там рекомендация **False**, это про другое): grid-инвентарь — это продукт работы стратегии, а не хедж-позиция, которую можно оставить «жить»; выход за диапазон означает, что модель (боковик) не подтвердилась, и правило проекта (`grid-bot-demo-run.md` §6, `grid-path.md` §1.4) уже фиксирует стоп как обязательный элемент, а не опцию. Внешние площадки (Binance/Pionex/Bitsgap) одинаково рекомендуют жёсткий stop-loss/ликвидацию при пробое диапазона грид-бота, а не «оставить висеть» [И1][И4][И5] — второй независимый источник этого решения.
3. Расчёт реализованного PnL сессии сетки (все арбитражи + результат финальной ликвидации) → **один** вызов `risk.record_pnl(inst_id, total_pnl, closed_at=now)` (не по каждому арбитражу — обоснование в §6.2).
4. `risk.block_instrument(inst_id, hours=4)` — cooldown **4ч** до повторного создания сетки на этом инструменте (короче общего 24ч cooldown после серии убытков `risk-core.md` §5 — это специфичный для grid «остыть после пробоя» таймер; если тот же пробой попутно запустил per-instrument loss-streak block на 24ч через `record_pnl`, действует более строгий — «strictest constraint wins», уже принятый принцип проекта, `risk-core.md` §1).
5. Событие в журнал риска (`risk events`, уже предусмотрено контрактом `risk.py`) + запись в `data/storage` в том же формате, что метрики нативного бота (см. §7) для последующего сравнения.

### 3.3 Зона предупреждения (soft, не блокирует)

Не обязательна для v1, но дёшева и снижает частоту хардстопов: при приближении цены к границе (например, в пределах одного шага сетки от `minPx`/`maxPx`, или классификатор режима перешёл из `Range` в `Mild Trend`) — увеличить частоту опроса (мониторинг вместо 4–8ч, как у нативного, до 15–30 мин) и залогировать предупреждение. Никаких сделок это состояние само по себе не меняет — решение остаётся за hard stop.

## 4. Сайзинг шага и уровней

### 4.1 Базовая формула (geometric, `runType=2`)

```
range_pct = (maxPx - minPx) / minPx × 100                 # 5–15%, см. §2
step_pct  = ln(maxPx / minPx) / gridNum × 100              # % на уровень (та же формула,
                                                            # что подтверждена эмпирически
                                                            # в grid-bot-demo-run.md: 0.29%)
gridNum   = round(range_pct / step_pct_target)             # ограничение биржи: 2–100
```

`runType=2` (geometric) выбран по той же логике, что уже задокументирована в проекте (`grid-path.md` §1.1, `grid-bot-demo-run.md` §1): равные %-шаги дают одинаковую прибыль на арбитраж в любой точке диапазона, что честнее для широких % коридоров, чем арифметические равные $-шаги. Это же предпочтение подтверждают независимые обзоры бирж/агрегаторов: geometric — стандартный выбор для волатильных/широких диапазонов, arithmetic — для узких стабильных [И6][И7].

### 4.2 Число уровней ограничено биржей, но не является первичным параметром

Число уровней — **производная** от `range_pct` и `step_pct`, а не независимо выбираемая переменная (в отличие от исходной формулировки `trend-grid-bot`, где волатильность определяла и ширину, и шаг одновременно — см. поправку ниже). Практический ориентир: избегать `gridNum < 10` (слишком грубая сетка, теряет смысл частых арбитражей) — если формула даёт меньше, штатная реакция — либо расширить диапазон (в рамках 5–15%), либо признать, что текущая волатильность/диапазон непригодны для сетки на этом инструменте сейчас.

### 4.3 Собственная поправка: минимальный шаг определяется экономикой комиссий, а не только волатильностью

`trend-grid-bot` (локальный скилл) рекомендует шаг 0.15–0.30% в зависимости от BB bandwidth, с нижней границей 0.15–0.18% при низкой волатильности. **Проверка показывает, что нижняя часть этого диапазона убыточна после комиссий на большинстве конфигураций** — см. §5.3 для вывода. Наш дизайн **поднимает пол шага до 0.32%** независимо от волатильности; волатильность в этом дизайне влияет на **ширину диапазона** (§2), не на нижнюю границу шага. Обоснование и расчёт — §5.3 (там же — почему это не противоречит уже работающему нативному боту).

## 5. Комиссии и проскальзывание

### 5.1 Тип ордера и ставка комиссии

Уровни сетки — это **отдыхающие лимитные ордера** (resting orders), которые исполняются при касании ценой уровня. По официальному объяснению механики комиссий OKX и независимому разбору: ордер, который лежит в стакане и исполняется позже (не сразу при выставлении), оплачивается по ставке **maker** (базовый тир — **0.08%**, тот же тир, что уже зафиксирован в `backtester-design.md` §3.1 [И8]); ордер, который исполняется мгновенно при выставлении (пересекает спред), — по ставке **taker** (0.10%) [И9][И10]. Для сетки в штатном режиме (диапазон выбран вокруг текущей цены, уровни выше/ниже неё) почти все исполнения — maker.

- **Базовый сценарий бэктеста:** round-trip fee = **0.08% × 2 = 0.16%** на арбитраж (buy на уровне `i`, sell на уровне `i+1`).
- **Стресс-сценарий (обязателен в отчёте, по аналогии с `backtester-design.md` §3.3):** если бар «прыгает» через несколько уровней сразу (гэп), первое пересечение внутри гэпа не обязано быть maker — считать этот фрагмент по taker (0.10% × 2 = 0.20%).

### 5.2 Проскальзывание

- **Базовый сценарий:** уровень — это заранее выставленный лимитный ордер по точной цене; при касании ценой уровня исполнение происходит **по цене уровня, без проскальзывания** (тот же принцип, что и у любого лимитного ордера — отличие от рыночных ордеров, для которых `backtester-design.md` даёт параметрические 5 бп). Эмпирика demo (`demo-slippage.md`) о проскальзывании **рыночных** ордеров сюда прямо не переносится — там измерялся другой тип ордера; для лимитного уровня сама постановка вопроса другая (не «насколько цена хуже эталона», а «исполнится ли по указанной цене»).
- **Стресс-сценарий:** на «гэп»-барах (свеча пробивает более одного уровня сетки за один бар) — дополнительные **+5 бп/сторону** на исполнения внутри гэпа (используем уже откалиброванный проектный дефолт из `backtester-design.md`/`demo-slippage.md`, не изобретаем новый), моделируя риск, что при быстром движении реальная глубина стакана на дальних уровнях хуже, чем на «touch» (эмпирически подтверждено для рыночных ордеров при $500–2000 в `demo-slippage.md` §7 — тот же порядок величины разумно использовать как консервативную оценку и для лимитных гэп-исполнений, пока нет отдельного замера).

### 5.3 Минимальный прибыльный шаг (ключевой расчёт)

```
fee_share = round_trip_fee / step_pct
```

Требование: `fee_share ≤ 0.5` (комиссии не должны съедать больше половины валовой прибыли на арбитраж) — тот же принцип, что уже принят в `backtester-design.md` §6 (критерий приёмки №7: «доля комиссий+проскальзывания в брутто-PnL < 50%»), здесь применённый как **предварительное условие конфигурации**, не только как отчётная метрика по факту прогона.

- При базовой ставке (maker round-trip 0.16%): `step_pct ≥ 0.16% / 0.5 = 0.32%`.
- При стресс-ставке (taker round-trip 0.20%): `step_pct ≥ 0.40%` — это ориентир, не жёсткий гейт (базовый сценарий реалистичен для штатной работы сетки, см. §5.1); отчёт бэктеста обязан показывать `fee_share` в обоих сценариях.

Независимая проверка формулы (без привязки к OKX) — два внешних источника с одинаковым выводом «шаг сетки обязан превышать комиссию за цикл»: [И11] Rebatly, «Grid Bot Fee Math: When Is Your Grid Actually Profitable?» (явная формула `min spacing = 2 × maker fee`); [И12] Money Flock, «Grid Bot Calculator» (то же требование, независимая площадка).

**Сверка с уже работающим нативным ботом:** шаг нативного бота — 0.29% (`grid-bot-demo-run.md` §1) → `fee_share = 0.16/0.29 ≈ 55%` — по нашему же критерию это чуть **хуже** целевых 50%. Вывод: нативный бот запущен как эталон/измерительный инструмент (задача `GRID-VERDICT` — оценить именно его метрики), не как образец конфигурации для нашей собственной реализации; для собственной сетки применяется более строгий пол 0.32%. Разница между 0.29% и 0.32% невелика (≈10%), это не переворачивает уже накопленные наблюдения по нативному боту, но фиксирует, что **наш** конфигуратор должен быть чуть консервативнее скилла `trend-grid-bot`.

**Почему это важно за пределами прибыльности одной сетки:** каждый убыточный (или почти нулевой из-за комиссий) арбитраж — это вызов `risk.record_pnl` с `pnl < 0` (если бы вызывался по каждому арбитражу — см. §6, почему в этом дизайне не вызывается) либо вклад в итоговый PnL сессии. Системная серия из **5** убытков подряд (по любому инструменту/стратегии) останавливает **все** стратегии на 24ч (`risk-core.md` §5, `SYS_LOSS_STREAK_PAUSE`) — недооценённые комиссии в сетке из-за слишком узкого шага не просто снижают её собственную доходность, а создают риск ложного срабатывания общесистемного breaker'а, если бы PnL сетки учитывался по-арбитражно. Это ещё один аргумент за агрегированный (не по-арбитражный) вызов `record_pnl`, см. §6.2.

## 6. Интеграция с `src/risk.py` (проверено по исходному коду, не только по контракту risk-core.md)

### 6.1 Критическая находка: entries/day и обслуживающие ордера сетки

Прочитан код (не только спецификация): `OrderRouter.place_order` вызывает `risk.register_entry(inst_id, side, risk_pct)` на **каждый** выставленный ордер (`src/order_router.py:229`), а `register_entry` инкрементирует **глобальный** (не per-instrument) счётчик `entries_today`, который `check_entry_allowed` блокирует при достижении **10** (`src/risk.py:36, 189`, `MAX_ENTRIES_PER_DAY = 10`). Grid-стратегия по своей природе многократно переставляет ордера на уровнях (после каждого исполнения — новый ордер на противоположной стороне); при активном рынке это легко десятки ордеров в день. Если каждая такая перестановка идёт через штатный путь `place_order`, счётчик 10/день исчерпается за часы и заблокирует **не только сетку, но и DCA/mean-reversion/рисковый карман** до 00:00 UTC (лимит глобальный).

**Решение (требование к GRID-IMPL, не к этой задаче):** обслуживающие ордера уровней сетки обязаны размещаться в обход инкремента `entries_today` — например, отдельным низкоуровневым методом роутера (или параметром `count_as_entry: bool`), используемым только сеточным модулем для операций «выставить/переставить уровень». Обязательный тест: симуляция сетки с ≥20 исполнениями за день не должна увеличивать `entries_today` больше чем на **1** (см. §8.2 — это конкретный, проверяемый пункт для GRID-BT-SIM/GRID-IMPL).

### 6.2 Жизненный цикл занятости риск-слота (`risk_open_risk`)

Ещё одна находка из чтения кода: `record_pnl` **безусловно** удаляет запись `risk_open_risk` инструмента при каждом вызове (`src/risk.py`, внутри `record_pnl`: `DELETE FROM risk_open_risk WHERE inst_id=?`), плюс инкрементирует/сбрасывает per-instrument `loss_streak`. Если вызывать `record_pnl` по каждому завершённому арбитражу сетки (естественный кандидат, т.к. каждый арбитраж — реально закрытая сделка), это (а) освобождает «слот» позиции сразу после первого же арбитража — открывая возможность другой стратегии одновременно занять тот же инструмент, пока сетка ещё активна (нарушает принцип «без хеджа на одном instId», уже принятый в `risk-core.md` §2, resilience-trader P3); (б) превращает нормальную частую работу сетки в поток мелких событий `loss_streak`, семантика которого рассчитана на дискретные направленные сделки, а не на десятки арбитражей в день.

**Принятая схема жизненного цикла (переиспользует существующий API `risk.py` без изменения сигнатур):**

| Событие | Вызов | Эффект |
| --- | --- | --- |
| Создание сетки | `check_entry_allowed(inst_id, side="neutral")` → если True: `register_entry(inst_id, "neutral", risk_pct=grid_risk_pct)` | Один раз: занимает слот `risk_open_risk` (блокирует хедж другой стратегией на этом instId, учитывается в portfolio heat ≤6%), инкрементирует `entries_today` на **1** |
| Исполнение уровня (buy/sell, много раз за жизнь сетки) | обслуживающее размещение ордера **в обход** `register_entry` (см. §6.1) | Не трогает `risk_open_risk`, не трогает `entries_today` |
| Завершённый арбитраж (buy@i → sell@i+1) | **не** вызывает `risk.py` напрямую — PnL арбитража копится во внутреннем состоянии grid-модуля (та же схема хранения, что для сравнения с нативным ботом, §7) | day_pnl/HWM не двигаются по каждому арбитражу; реальная защита от просадки в это время идёт через уже существующий периодический `risk.update_equity(totalEq)` (см. ниже) |
| Остановка сетки (плановая или hard stop §3) | **один** вызов `record_pnl(inst_id, total_realized_pnl, closed_at=now)` с суммарным PnL всей сессии (все арбитражи + результат финальной ликвидации, если hard stop) | Освобождает `risk_open_risk`, обновляет day_pnl/HWM/loss_streak **на уровне сессии целиком** — семантически верная гранулярность («эта сетка в целом — выигрыш или проигрыш»), не зашумляется десятками мелких точек |
| Hard stop дополнительно | `block_instrument(inst_id, hours=4)` | Cooldown до повторного создания сетки (см. §3.2 п.4) |

**Почему real-time защита от просадки не теряется**, несмотря на отложенный `record_pnl`: движок (`src/engine.py:205-217`) уже сейчас периодически вызывает `risk.update_equity(account.totalEq)` — эквити с биржи, включающий **весь** нереализованный/реализованный результат аккаунта, включая работающие grid-позиции; сам код это прямо документирует («без этой проверки breakers видели бы только реализованный PnL из record_pnl, а нереализованный убыток (открытые позиции, grid-боты) не останавливал бы входы»). Это значит: дневной −6% и глобальный −15% breaker сработают в реальном времени по фактическому эквити независимо от того, когда именно сетка сама отчитается через `record_pnl`. Дополнительная интеграция для этого не требуется — только подтвердить на demo, что цикл опроса `totalEq` не отключён на время работы сетки (уже часть штатного мониторинга движка).

### 6.3 Сайзинг `quoteSz` через существующий `size_position`

Grid не имеет одного стоп-расстояния на сделку (в отличие от направленной позиции), но имеет естественный worst-case — выход за границу диапазона. Дизайн трактует ближайшую границу как «стоп» для целей сайзинга:

```
risk_cap  = size_position(equity, entry=center_price, stop=ближайшая_граница(minPx|maxPx),
                          ct_val=1, lot_sz=lotSz, min_sz=minSz, risk_pct=grid_risk_pct).notional
hard_caps = min(equity × 15%, оставшийся_бюджет_portfolio_heat)      # уже действующие потолки risk.py
quoteSz_max = min(risk_cap, hard_caps)
quoteSz_min = min_investment(REST) × 3                                # запас; факт. пример проекта — ×11.6
```

Если `quoteSz_min > quoteSz_max` — сетка **не создаётся** в текущих условиях (недостаточно бюджета под одновременно риск-лимит и минимальную инвестицию биржи); это осознанный fail-safe, не понижение порогов. `grid_risk_pct` — стартовый дефолт **min(2.0, оценка через range_pct/2 × quoteSz/equity)**, тот же потолок 2%, что и для любой другой сделки (`MAX_RISK_PCT` в risk.py) — подлежит калибровке вместе с остальными порогами (задача `RISK-CALIB`).

## 8. Критерии входа в бэктест

Адаптация общих критериев `backtester-design.md` §6 к path-dependent (не «сигнал на баре») природе grid. Часть критериев применяется как есть, часть — с оговоркой, часть — новые, специфичные для grid.

### 8.1 Архитектурное условие (предварительное, для BT-IMPL/GRID-BT-SIM)

Бэктестер в текущей спецификации (`backtester-design.md`) построен вокруг модели «сигнал на закрытии бара → исполнение на открытии следующего». Grid — не сигнальная стратегия: уровни — это заранее выставленные лимитные ордера, которые исполняются при касании ценой независимо от «сигнала на баре». Это требует отдельного примитива движка — «resting limit order, fill-if-touched» (проверка `low ≤ level_px ≤ high` внутри подтверждённого бара, обработка «low раньше high» при нескольких уровнях в одном баре, замена исполненного уровня на противоположный после каждого филла). Такой примитив полезен не только для grid — любая будущая лимит-ордерная стратегия будет на него опираться. **Это условие входа в бэктест, а не отдельная стратегия**: пока примитив не реализован и не покрыт тестами (см. задачу `GRID-BT-SIM` ниже), backtest для grid запускать нельзя.

### 8.2 Обязательные тесты (аналог slicing/recursive-тестов для сигнальных стратегий)

1. **Anti-lookahead для уровней:** решение о филле уровня в баре `t` использует только OHLC бара `t` (никогда — данные `t+1` и позже); тест — усечение ряда не должно менять уже принятые решения о филлах (тот же slicing-принцип, что в `backtester-design.md` §1.2).
2. **Fee-floor pre-check:** конфигурация, не удовлетворяющая `fee_share ≤ 0.5` при базовой (maker) ставке, отклоняется бэктестером на этапе валидации конфига — до прогона, не по факту (§5.3).
3. **Entries/day изоляция (§6.1):** симуляция сетки с ≥20 исполнениями за модельный день не должна инкрементировать симулированный `entries_today` больше чем на 1.
4. **Хардстоп определяется корректно (§3.1):** синтетический прогон на данных с чётким пробоем диапазона (например, исторический трендовый отрезок BTC, специально взятый вне Range-режима) обязан завершиться срабатыванием стопа, ограничивающим убыток заранее рассчитываемой величиной — а не «замороженной» позицией без выхода.
5. **Non-triggering на боковике:** тот же тест в обратную сторону — прогон на спокойном боковом окне не должен вызывать ложных хардстопов (иначе гейт с задержкой/шагом §3.1 требует калибровки).

### 8.3 Данные и режимные окна

- ≥3 непересекающихся исторических окна по ≥30 дней каждое, отобранные так, чтобы каждое окно **классифицировалось как Range** большую часть времени по классификатору §1 (иначе тест не про grid, а про то, что фильтр входа работает — это отдельная, тоже нужная, но другая проверка).
- Суммарно ≥30 завершённых арбитражей на окно (тот же статистический пол, что и общий критерий `backtester-design.md` §6 п.5, адаптированный к единице «арбитраж» вместо «сделка»).
- Отчёт обязателен по обоим сценариям комиссий/проскальзывания (§5.1–5.2: базовый и стресс).
- **Фиделити-проверка к нативному боту:** прогон собственного симулятора на том же историческом окне, что и текущий 48-часовой прогон нативного бота (`grid-bot-demo-run.md`), с теми же параметрами диапазона — расхождение симулированного `gridProfit`-эквивалента с фактическим `gridProfit` нативного бота фиксируется (не обязан быть нулевым — разная модель исполнения, разные округления), но обязано быть в разумных пределах (стартовый ориентир — ±20%, калибруется по факту первого прогона) как проверка правдоподобия симулятора, прежде чем доверять ему для конфигураций, которые нативный бот не пробовал.

### 8.4 Итоговый gate

Стратегия допускается к demo, если: (а) все тесты §8.2 зелёные, (б) в ≥2 из 3 окон §8.3 итог positive net of fees, суммарно — positive, (в) фиделити-проверка в допуске, (г) `fee_share` в базовом сценарии ≤50%, в стресс-сценарии — зафиксирован в отчёте (не обязателен ≤50%, но не должен систематически переворачивать знак суммарного PnL окна).

## 9. Критерии входа в demo

1. Backtest gate §8.4 пройден.
2. Синтетический (без реальных ордеров) dry-run модуля на demo-данных в реальном времени ≥ несколько часов — 0 необработанных исключений, 0 несогласованных состояний уровней (каждый уровень либо `resting`, либо `filled+replaced`, без «повисших» промежуточных состояний).
3. Затем — реальный demo-прогон **≥48ч** (тот же период, что бенчмарк нативного бота — `grid-bot-demo-run.md`, для сопоставимости условий рынка при последующем сравнении), с находящимся в силе критерием остановки §3: если правило сработало — оно обязано было сработать корректно (позиция ликвидирована, cooldown применён, запись в журнал); если не сработало — цена действительно оставалась в диапазоне весь период (перепроверяется независимо по свечам/тикеру).
4. Ноль зависших ордеров после демо-прогона (та же проверка, что уже стандартна в проекте — `P1-LOAD`, `P1-WSDROP`).
5. Проверка §6.1 на реальных данных: `entries_today` не растёт быстрее, чем на 1 за создание сетки (не считая обслуживающих ордеров).
6. Только после этого — соответствие общему критерию выхода Фазы 2 из roadmap (walk-forward/режимные окна + ≥7–14 дней paper/dry-run без аномалий) наравне с другими стратегиями Фазы 2.

## Открытые вопросы

1. **Формула `grid_risk_pct` для `register_entry`/`size_position` (§6.3)** — стартовый дефолт предложен (`min(2.0, range_pct/2 × quoteSz/equity)`), не откалиброван; уточняется вместе с существующей задачей `RISK-CALIB` после накопления статистики.
2. **Точный способ «обхода» `register_entry` для обслуживающих ордеров сетки (§6.1)** — новый параметр роутера vs отдельный низкоуровневый метод размещения; решение — за Insight Executor при реализации `GRID-IMPL`, здесь зафиксировано только требование (тест на неизменность `entries_today`).
3. **Допуск фиделити-проверки ±20% (§8.3)** — эвристический стартовый порог, требует калибровки по факту первого прогона `GRID-BT-SIM`/`GRID-IMPL` на историческом окне нативного бота.
4. **Порог `breakout_confirm_seconds=30` и «1 доп. шаг» для мгновенного триггера (§3.1)** — стартовые дефолты по аналогии с OKX `delaySeconds` и общей практикой pump protection, не откалиброваны на живых данных; калибровать вместе с §8.2 тестом «non-triggering на боковике».
