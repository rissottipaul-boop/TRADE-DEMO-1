# Деплой сервера 24/7 со статическим IP для live-торговли

- **Дата:** 2026-09-24 (обновлено 2026-09-24: регион матчинга OKX — переезд Гонконг→Токио уже состоялся, факт перепроверен)
- **Тема:** Требования к серверу для непрерывной работы движка/live-runner, варианты провайдера, план переноса с локальной Windows-машины
- **Статус:** validated (требования и цены — по официальным страницам провайдеров и OKX, проверено 24.09.2026), выбор конкретного тарифа и оплата — открытый вопрос человеку
- **Задача:** DEPLOY-VPS (доска `ops/board.md`) — обязательна до перевода CARRY-IMPL и любой live-стратегии на реальные деньги

> Это исследование инфраструктуры, а не финансовый совет. Цены облачных провайдеров меняются точечными акциями — перед оплатой сверить с текущим прайсом на сайте.

## 1. Зачем это вообще нужно

- Live-ключ OKX с торговыми правами теряет доступ, если приходит не с разрешённого IP: в настройках ключа можно привязать **до 20 IP-адресов** (через запятую/пробел); запросы с других IP отклоняются. Ключ с правами `trade`/`withdraw`, **не привязанный ни к одному IP**, OKX удаляет через 14 дней неактивности — привязка IP факультативна, но настоятельно рекомендована и по факту обязательна для длительной работы автоматики [И1].
- Домашний IP большинства провайдеров у пользователя — динамический (DHCP переподключение меняет его), поэтому текущая локальная Windows-машина не годится для live: смена IP = блокировка API-ключа без предупреждения. Нужен внешний хост со стабильным адресом.
- Даже без live прямо сейчас, `LIVE-PREFLIGHT` уже проверяет поле `ip` в `account/config` и предупреждает «до DEPLOY-VPS» — задача в зависимостях к CARRY-IMPL и любому будущему live-рукаву.

## 2. Требования к серверу

| Требование | Детали |
| --- | --- |
| **Статический IP** | Обязательно. У всех рассматриваемых провайдеров (Vultr, DigitalOcean, Hetzner, Contabo) статический IPv4 включён в тариф по умолчанию — привязывается к инстансу, не меняется при перезагрузках. Проверить это в панели провайдера при заказе — не путать с эфемерным IP у некоторых serverless/PaaS-продуктов. |
| **Регион / задержка до OKX** | **Переезд состоялся: матчинг-движок и все latency-sensitive сервисы OKX уже перенесены с Alibaba Cloud в Гонконге в дата-центр Токио**, миграция завершена к концу июля 2026 (первоначально планировали июнь, сдвинули), заявлено zero-downtime, без изменений API-эндпоинтов и полей [И3][И3b]. Независимое подтверждение по факту: мониторинг Glassnode зафиксировал переворот задержек — из Токио RTT упал с ~52 мс до ~4 мс, из Гонконга вырос с ~5 мс до ~63 мс — то есть матчинг физически теперь в Токио, а не в Гонконге [И9]. **Вывод: регион сервера для минимальной задержки — Токио, не Сингапур/Гонконг.** Для стратегий проекта (grid/DCA/carry, не HFT) разница между 4 мс (Токио) и ~15–30 мс (Сингапур/Гонконг) некритична функционально, но раз цены сопоставимы (см. §4) — предпочтителен Токио. США/Европа (150–250+ мс) по-прежнему не годятся. |
| **ОС** | Два варианта — см. §3. |
| **Автозапуск при перезагрузке** | Windows: Task Scheduler (`schtasks /create` при логоне/старте системы) либо служба через NSSM, запускающая `ops\engine.ps1 start` / `ops\live.ps1 start`. Linux: `systemd`-юниты (`engine.service`, `live-runner.service`) с `Restart=on-failure`, `WantedBy=multi-user.target`. |
| **Мониторинг** | Минимум: внешний uptime-чекер (UptimeRobot/healthchecks.io бесплатный тир) на HTTP-пинг или `python -m src.ops status`, плюс алерт в Telegram/email при недоступности > 5 мин. Локально — то, что уже есть в `ops/hooks` и Ops Sentinel, просто перенести на сервер. |
| **Бэкап `data/`** | `data/*.db` (SQLite: `bot_state.db`, `risk_state.db`), `data/pump_journal.jsonl`, конфиги (`ops/*.json`, `.env` — **не** коммитить, хранить бэкап зашифрованным/приватным). Простой вариант: ежедневный `cron`/Task Scheduler job, копирующий `data/` в объектное хранилище провайдера (Vultr Object Storage / DO Spaces / Hetzner Storage Box) или хотя бы в отдельный снапшот диска раз в сутки. |

## 3. ОС: Windows Server vs Linux — оценка миграции

### Вариант A — Windows Server VPS (без миграции кода)

- Все текущие `ops/*.ps1` (`engine.ps1`, `live.ps1`) запускаются как есть, PowerShell пре-инсталлирован.
- Минус: у большинства бюджетных провайдеров (Vultr, DO, Hetzner, Contabo) Windows Server — **платная лицензия поверх тарифа**: у Vultr это отдельные +$15–18/мес к базовому тарифу за лицензию [И4]. Hetzner/Contabo Windows-образы тоже с наценкой, доступность зависит от плана.
- Автозапуск: Планировщик заданий Windows (Task Scheduler) с триггером «При запуске системы», действие — запуск `powershell.exe -File ops\engine.ps1 start` (и аналогично для `live.ps1`). Работает без правок кода.
- **Трудозатраты: низкие** (перенос — несколько часов: RDP, установка Python/venv, копирование репо, настройка Task Scheduler, тест).

### Вариант B — Linux VPS + перенос `.ps1` → кроссплатформенно

- Плюс: Linux VPS в среднем **в 2–3 раза дешевле** (нет лицензии ОС, шире выбор дешёвых тарифов), `systemd` — более стандартный и надёжный инструмент автозапуска/рестарта для 24/7-сервисов, чем Task Scheduler.
- Минус (миграция): `ops/engine.ps1` и `ops/live.ps1` — **обвязка вокруг PID-файла, флагов `data/STOP_ENGINE`/`data/KILL`, логов**; сам Python-код (`src/engine.py`, `src/live_runner.py`, `src/config.py` и остальные модули) уже кроссплатформенный — путей вида `C:\...` или `win32`-вызовов в `src/` не найдено (проверено `grep` по `os.name|platform.system|win32|pywin32` — совпадений в `src/*.py` нет, только текстовые упоминания `.ps1` в докстрингах). Значит, **переносить нужно только обвязку**, а не бизнес-логику.
- Объём переноса: 2 файла `ops/engine.ps1` (71 строка) и `ops/live.ps1` (аналогичный размер) → эквивалентные `systemd`-юниты + при желании bash-обёртки для ручных команд (`start/stop/status`). Плюс переиздать пути (`.venv/Scripts/python.exe` → `.venv/bin/python`), убедиться, что `Get-CimInstance Win32_Process` (проверка PID) заменена на `psutil`/`/proc/<pid>/cmdline`.
- **Трудозатраты: средние** (оценка 0.5–1 рабочий день на перенос + тестовый прогон engine/live-runner на demo сутки).

### Рекомендация по ОС

Для **первого** сервера — **Windows Server VPS**, чтобы не блокировать DEPLOY-VPS миграцией и быстрее получить статический IP под live-ключ (низкие трудозатраты, код трогать не нужно). Перенос на Linux — отдельная задача с более низким приоритетом (экономия ~$10–15/мес при поднятом уже риске миграции), кандидат на Фазу после первого стабильного live-трека.

## 5. План переноса (по шагам)

1. Заказать VPS (провайдер и тариф — решение человека, §6).
2. **Вариант Windows:** RDP на сервер → установить Python 3.x (та же версия, что локально) → скопировать репозиторий (git clone или zip) → создать `.venv`, `pip install -r requirements.txt` → скопировать/пересоздать `.env` (секреты — вручную, не через общий канал) → прогнать `python -m src.ops status` на demo → настроить Task Scheduler на `ops\engine.ps1 start` при старте системы → тестовый рестарт сервера, проверить автозапуск.
   **Вариант Linux:** аналогично, но вместо RDP — SSH; вместо `.ps1` — новые bash-скрипты/`systemd`-юниты (задача для Insight Executor, не входит в этот инсайт); `.venv/bin/python`.
3. Настроить IP-whitelist в OKX API-ключе (в разделе управления API-ключами) на публичный IP нового сервера — сделать **после** проверки, что сервер стабильно поднимается (иначе при пересоздании инстанса IP может измениться, и потребуется обновить whitelist).
4. Настроить мониторинг (UptimeRobot/healthchecks.io) и Telegram-алерт.
5. Настроить бэкап `data/` по расписанию (ежедневно, retention 7–14 дней).
6. Прогнать demo-режим на новом сервере параллельно с локальной машиной ≥ 24–48 часов, сравнить логи/метрики, затем выключить локальный запуск и оставить единственный источник правды — сервер.
7. Только после стабильного прогона — переводить live-ключ на IP сервера (зависит от решений LIVE-SETUP/GUARD-LIVE-PATCH на доске).

## 7. Открытые вопросы

1. ~~Точная дата переноса матчинг-движка OKX Гонконг→Токио~~ — **закрыто.** Переезд состоялся к концу июля 2026 (первоначально планировали июнь, был перенесён). Проверено двумя официальными страницами OKX — глобальной (canonical `www.okx.com/help/okx-trading-server-migration-announcement-hong-kong-tokyo`, без пометки «US»/«INC.», относится к основному сайту okx.com, которым пользуется проект) и для юрлица OKX INC./US (`.../okx-us-trading-server-migration-announcement-hong-kong-tokyo`) — обе с идентичным содержанием и датой [И3][И3b]. Независимое подтверждение факта миграции (не только план) — три вторичных источника, ссылающиеся на данные мониторинга Glassnode: RTT из Токио упал с ~52 до ~4 мс, из Гонконга вырос с ~5 до ~63 мс, что возможно только если матчинг физически переехал [И9]. Итог: ≥ 2 независимых первичных (обе официальные страницы OKX) + ≥ 2 вторичных с эмпирическими данными — уровень подтверждения выше обычного validated.
   - Ограничение эмпирической проверки своими силами: `www.okx.com` и `ws.okx.com` идут через Cloudflare (проверено `Test-Connection`/`Resolve-DnsName` 24.09.2026 — резолвится в anycast-IP Cloudflare, напр. `172.64.144.82`, `104.18.43.174`), поэтому прямой ping/traceroute с локальной машины меряет RTT до ближайшей точки присутствия Cloudflare, а не до бэкенда матчинга — самостоятельно подтвердить регион backend этим способом нельзя. Если нужна собственная эмпирика (а не только вторичные источники): поднять пробный VPS в Tokyo и в Singapore, замерить RTT WS-пинг-понга приватного канала OKX (`ws-private` ping/pong latency, публичные REST-таймстемпы `GET /api/v5/public/time`) из обеих точек и сравнить — не требует API-ключей с торговыми правами.
2. Нужен ли провайдеру KYC/верификация для оплаты картой/крипто из региона пользователя (уточнить при выборе конкретного провайдера).
3. Формат объектного хранилища для бэкапов `data/` (Vultr Object Storage / Hetzner Storage Box / просто ежедневный zip на второй диск) — решить вместе с задачей на реализацию бэкапа.
