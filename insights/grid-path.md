## 1. Параметры биржевого grid-бота (okx CLI 1.4.8, скилл okx-cex-bot)

### 1.1 Создание — `okx bot grid create` (REST: `POST /api/v5/tradingBot/grid/order-algo`)

| Параметр | Обяз. | Смысл | Заметки для проекта |
|---|---|---|---|
| `--instId` | да | `BTC-USDT` (спот) / `BTC-USDT-SWAP` (контракт) | Фаза 1 — только спот |
| `--algoOrdType` | да | `grid` (спот) или `contract_grid` | Несовпадение с реальным типом бота → ошибка `50016`; всегда брать из `bot grid orders` |
| `--maxPx` / `--minPx` | да | Верхняя/нижняя границы диапазона | Выход цены за границы = «заморозка» сетки (ключевой риск) |
| `--gridNum` | да | Число уровней, **2–100** | Расчёт от волатильности — см. §1.4 |
| `--runType` | нет (def 1) | `1`=арифметический шаг (равные $-интервалы), `2`=геометрический (равные %-интервалы) | Для широких диапазонов геометрический честнее; trend-grid-bot использует `2` |
| `--quoteSz` / `--baseSz` | усл. | Инвестиция в USDT / в базовой валюте — **только спот**, одно из двух | Помним: практический minNotional BTC-USDT ~$1–5 на ордер (phase0-smoke-test) |
| `--direction` | усл. | `long`/`short`/`neutral` — **обязателен для contract_grid** | Для спота не применим |
| `--lever`, `--sz`, `--basePos` | усл. | Плечо, маржа, открытие базовой позиции — только contract_grid | Фаза 2+ |
| `--tpTriggerPx`/`--slTriggerPx` | нет | Абсолютные TP/SL-триггеры всей сетки | Взаимоисключающие с `--tpRatio`/`--slRatio` (ratio — только contract). Это и есть «стоп всей сетки» из открытого вопроса №1 spot-strategies.md |
| `--algoClOrdId` | нет | Клиентский ID (1–32 символа), идемпотентное создание | Использовать в нашем оркестраторе против дублей при ретраях |

### 1.2 ai-param и min-investment (REST, публичные)

- `GET /api/v5/tradingBot/grid/ai-param` — **публичный** AI-подбор параметров сетки от биржи (бэктест OKX: диапазон, gridNum, ожидаемая доходность по истории). В модуле grid также заявлен публичный эндпоинт RSI back-testing.
- `POST /api/v5/tradingBot/grid/min-investment` — **публичный** расчёт минимальной инвестиции под заданную конфигурацию (чтобы каждый уровень сетки проходил minSz/minNotional).
- ⚠️ **Оба эндпоинта НЕ экспонированы в okx CLI 1.4.8** (в SKILL.md okx-cex-bot их нет) — вызывать напрямую через REST (ai-param/min-investment без auth; порядок через CLI). Это задача для нашего коннектора `src/connector.py`, а не ручной операции.
- Ценность для проекта: **эталон для калибровки** — сравнить AI-параметры OKX с собственным расчётом от ATR (открытый вопрос №3 spot-strategies.md) и использовать min-investment как pre-flight валидацию перед созданием сетки.

### 1.3 Чтение PnL и sub-orders

- `okx bot grid details --algoOrdType grid --algoId <id>` → конфиг + `pnlRatio`, состояние, инфо о позиции. По trend-grid-bot из details извлекаются: `gridProfit` (реализованная прибыль арбитражей сетки), `floatProfit` (нереализованный PnL), `filledCount` (число исполнений); итоговая доходность = `(gridProfit + floatProfit) / sz × 100`.
- `okx bot grid sub-orders --algoId <id>` → исполненные сделки сетки (по умолчанию) или висящие уровни (`--pending`, работает в демо); `--groupId` группирует пару buy→sell одного «арбитража» сетки; пагинация `--after/--before/--limit` (def 100).
- `okx bot grid stop --stopType 1` — чистый выход (спот: продать base обратно в quote); `--stopType 2` — оставить активы/позицию (для contract потом `close-position`).
- `okx bot grid amend` — на лету меняет диапазон (`maxPx`/`minPx`/`gridNum` вместе) и/или TP/SL; `topUpAmt` — довнесение маржи (contract). Это наш механизм «пересоздания сетки» без полного стопа.

### 1.4 Параметризация от волатильности (из trend-grid-bot и dca-bot-parameterizer)

- Ширина диапазона: 5–15% вокруг текущей цены; при выходе цены — пересчёт и amend/пересоздание.
- Число уровней: целевой шаг 0.15–0.30% (geometric); `gridNum = round(range_pct / target_spacing)`, при высокой волатильности (BB bandwidth > 8%) шаг 0.25–0.30% → 25–35 уровней; ограничение 20–100.
- dca-bot-parameterizer: режим рынка по EMA20 (Strong/Mild Trend/Range), волатильность = `ATR% = ATR/price`, режим волатильности по отношению к 20-барному среднему ATR% (Low/Normal/High). Grid имеет смысл только в **Range** — тот же классификатор переиспользуем как фильтр входа для своей сетки.

## 2. Матрица решения: биржевой бот vs своя реализация

| Функция | Биржевой grid-бот OKX | Своя реализация |
|---|---|---|
| Исполнение уровней сетки | ✅ нативно, сервер-side, без локального процесса, без WS-инфраструктуры | требует ордер-менеджмент, reconciler, WS |
| AI-подбор параметров / min-investment | ✅ из коробки (REST) | нужно строить самим (но эталон есть) |
| TP/SL всей сетки, amend диапазона | ✅ `tpTriggerPx`/`slTriggerPx`, `amend` | полный контроль |
| Кастомные фильтры входа (режим рынка, funding, сигналы) | ❌ невозможно — логика внутри OKX | ✅ |
| Триггер старта по условию | частично (`triggerStrategy` instant/price/rsi/webhook у contract-grid) | ✅ любой |
| Интеграция с риск-модулем `src/risk.py` (лимиты, circuit breakers) | ❌ только внешний надзор: мониторинг + stop по нашим правилам | ✅ нативно |
| Реакция на выход из диапазона (остановка всей сетки по правилам проекта) | ⚠️ вручную/надзором: amend или stop; «заморозка» с убыточной позицией — ответственность надзора | ✅ автоматическая политика (stop-всей-сетки / перенос диапазона / хедж) |
| Метрики и журнал сделок для бэктеста-сравнения | ⚠️ sub-orders доступны, но выгружать и нормализовать надо нам | ✅ полный контроль данных |
| Зависимость от биржевого сервиса | ❌ бот живёт на OKX (простой/изменение API — наш риск) | ✅ только ордерное API |

**Вывод:** биржевой бот = быстрый валидатор и эталон доходности; своя сетка = носитель кастомных сигналов и риск-политик. Это не «либо-либо», а этапы одного пути.

## 3. Рекомендуемый план Фаз 1–2

**Порядок (подтверждает roadmap, задача p1-grid-demo-bot):**
1. **Фаза 1, биржевой grid в демо:** spot grid BTC-USDT, ≥48 ч непрерывной работы. Создание через `okx bot grid create` с параметрами: диапазон от ATR%/BB-методики (§1.4), `runType=2` (geometric), `gridNum` 25–35, `quoteSz` ≥ min-investment (проверить через REST min-investment), обязательно `--slTriggerPx` ниже диапазона (страховка «заморозки»). Перед созданием — сверка с `ai-param` (REST): зафиксировать расхождение наших параметров с AI OKX.
2. **Надзор в демо (наш код, минимальный):** периодический опрос `details` + `sub-orders`; правило остановки: цена вне диапазона > N минут или `pnlRatio` < порога → `stop --stopType 1`. Это первый use-case связки с будущим `src/risk.py` (пока как внешний supervisor).
3. **Выводы Фазы 1** → документ сравнения (метрики ниже) → решение по критерию §4.
4. **Фаза 2, своя реализация:** собственный grid-модуль поверх `src/connector.py`/`src/reconciler.py` с фильтром входа (Range-классификатор из dca-bot-parameterizer), риск-политиками `src/risk.py`, автостановкой всей сетки при выходе из диапазона. Биржевой бот остаётся эталоном для A/B-сравнения на одних и тех же рыночных окнах.

**Метрики у биржевого бота (собирать в пригодном для сравнения виде):**
- `gridProfit` и `floatProfit` (details) со снапшотами по времени → кривая PnL, а не только итог;
- число завершённых арбитражей сетки: пары buy→sell по `groupId` из sub-orders (filled), с ценами/объёмами/временем → средняя прибыль на арбитраж, частота арбитражей в час;
- `filledCount` и средний интервал между исполнениями;
- **время в диапазоне**: доля времени, когда цена внутри [minPx, maxPx] (считаем сами по тикеру/свечам — бот этого не отдаёт);
- **проскальзывание/исполнение**: разница цен исполнения sub-orders против теоретических уровней сетки (уровни вычислимы из maxPx/minPx/gridNum/runType) + комиссии;
- число amend/stop-событий и причина (наш журнал надзора).

Формат: единая таблица/JSON-снапшоты в `src/storage`, чтобы своя реализация писала те же поля — тогда сравнение биржевой vs своя становится прямым.

## 4. Критерий «своя сетка нужна / не нужна»

**Переходим к своей реализации (need), если за ≥48 ч демо наблюдается хотя бы одно:**
1. Цена выходила из диапазона, и сетка «замёрзла» с убыточной позицией — т.е. требуется автополитика выхода, недоступная биржевому боту (подтверждено хотя бы одним событием).
2. Фильтр входа дал бы измеримый выигрыш: периоды, когда наш Range-классификатор говорил «не входить», а бот работал и показывал отрицательный/нулевой gridProfit.
3. Потребность в риск-интеграции подтвердилась: срабатывание (или near-miss) порогов `pnlRatio`/просадки, которыми должен управлять `src/risk.py`, а не ручной надзор.
4. Частота арбитражей сетки слишком низкая при AI-параметрах OKX, и наш ATR-расчёт параметров на тех же данных обещает заметно лучше (расхождение ai-param vs наш расчёт > 20% по gridNum/диапазону при лучшей симулированной доходности).

**Своя сетка НЕ нужна (отложить), если:** биржевой бот за демо-период показал приемлемый gridProfit при нулевых «заморозках», расхождение ai-param с нашим расчётом мало, а риск-надзор ни разу не понадобился. Тогда биржевой бот остаётся рабочей grid-стратегией, а усилия Фазы 2 идут в сигнальные стратегии (mean-reversion/trend) и риск-модуль.
