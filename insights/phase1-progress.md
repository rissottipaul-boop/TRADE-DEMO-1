# Фаза 1 — прогресс: данные и исполнение

- **Дата:** 2026-09-24
- **Статус:** в работе (основные компоненты реализованы)

## Реализовано

### 1. WebSocket-клиент (`src/ws_client.py`)

- Public и private (login `HMAC(ts+GET+/users/self/verify)`), хосты по региону из `OKX_DOMAIN`
- Heartbeat ping каждые 25 сек, тишина > 50 сек → reconnect; backoff 5с → 60с
- После reconnect: повторный login + все подписки одним запросом; стаканы инвалидируются до нового snapshot
- `notice 64008` → переподключение сразу (раньше приём блокировался на 55 сек)
- Исключение в обработчике стратегии не рвёт соединение

### 2. Локальный стакан (`OrderBook`)

- `action` (snapshot/update) читается с **верхнего уровня** сообщения
- Целостность — цепочка `prevSeqId == seqId` предыдущего сообщения; разрыв → ресинк (переподписка → свежий snapshot). Корректно обрабатывает heartbeat (`seqId == prevSeqId`) и сброс seqId после техработ
- Checksum (если биржа снова начнёт его слать) считается по **исходным строкам** цен/объёмов
- Рассинхронизированный стакан наружу не отдаётся (`get_book()` → `None`)

### 3. Хранилище состояния (`src/storage.py`)

- SQLite (WAL): `orders` (+`cl_ord_id`), `positions`, `trades` (ключ `inst_id + trade_id`, `fee_ccy`), `equity_curve`, `ws_state`
- Состояния ордеров — сырые OKX (`live`/`partially_filled`/`filled`/`canceled`); конечные состояния «липкие», `filled_sz` не убывает — запоздалый ответ REST не откатывает fill из WS
- Миграции схемы через `PRAGMA user_version` (v0 → v1)

### 4. Реконсилятор (`src/reconciler.py`)

- Сырые эндпоинты OKX (`orders-pending` с пагинацией, `trade/order`, `trade/fills`, `account/positions`): ключи в БД — `instId`, как в WS
- Пропавший из активных ордер — запрос финального статуса (`filled`/`canceled`), а не слепая пометка canceled
- Метрики рассинхрона: `missing_on_exchange`, `missing_locally`, `changed`
- Догрузка сделок из `/trade/fills` (идемпотентно, с пагинацией)

### 5. Движок (`src/engine.py`)

- `TradingEngine`: config → connector → storage → reconciler → risk → ws public + private (`orders`)
- REST-вызовы CCXT — в потоках (`asyncio.to_thread`), event loop и WS-пинги не блокируются
- `place_order`: риск-проверка входа (`risk.check_entry_allowed` + потолок notional 15% equity) → свой `clOrdId` → `expTime` **в HTTP-заголовке**; при сетевой ошибке ордер ищется по `clOrdId`
- Equity = `totalEq` аккаунта (раньше писался только USDT-баланс); передаётся в риск-ядро
- Kill-switch: файл `data/KILL` или `python -m src.ops kill` — отмена всех ордеров (включая algo) + остановка нативных grid-ботов
- Метрики прогона (`reconciles`, `divergences`, `errors`, reconnects) — в `ws_state.engine_stats`, смотреть `python -m src.ops status`

## Дополнение 2026-09-24: внешние ордера ≠ рассинхрон (RECON-EXT)

**Проблема.** Реконсилятор считал divergence любой ордер, которого нет в
локальной БД (`missing_locally`), и подбирал его в БД. Внешний ордер
(нагрузочный тест `lt*`, ручной, `pump*`), подобранный таким образом, при
внешней отмене давал ложный `missing_on_exchange` — именно так появился
`divergences: 1` в нагрузочном тесте выше. Это зашумляло критерий P1-72H
(`divergences == 0` за 72 часа).

**Решение.** «Свой» ордер определяется по префиксу `clOrdId`:
`OWN_CLORD_PREFIX = "bot"` — значение по умолчанию
`connector.new_client_order_id()`, через него ставят ордера движок и все
стратегии (order_router). Всё без префикса `bot*` — внешнее, включая пустой
`clOrdId` (ручные ордера): наши потоки выставления всегда проставляют свой
`clOrdId` (он же ключ восстановления после таймаута place). Выбор префикса,
а не наличия в БД, сознательный: WS-канал `orders` доставляет вообще все
ордера аккаунта, и движок пишет их в БД — то есть внешний ордер может
присутствовать локально, но своим от этого не становится.

**Что изменилось в `Reconciler.sync_orders`:**
- в сверке участвуют только свои ордера (и локальные, и биржевые фильтруются
  по `is_own_order`);
- внешние ордера с биржи попадают только в новую метрику `external_orders`
  и **не подбираются** в БД реконсилятором;
- `divergences` движка = `missing_on_exchange + missing_locally + changed`
  по-прежнему, но теперь только по своим ордерам — реальные рассинхроны
  (свой ордер есть локально, но пропал/отличается на бирже; свой ордер на
  бирже неизвестен локально).

**Почему критерий P1-72H остаётся значимым.** Метрика по-прежнему ловит всё,
что может пропустить WS по своим ордерам: пропавшие fill'ы, внешние отмены
своих ордеров, устаревшие состояния. Из критерия убран только шум от ордеров,
которые движок не ставил и не должен отслеживать. Известный компромисс:
внешний ордер, записанный в БД по WS и потом отменённый в обход WS, останется
в БД висеть в состоянии live (реконсилятор его не трогает) — на метрики и
торговлю это не влияет.

**Проверка.** `tests/test_storage_reconciler.py`: регрессия (свой ордер с
биржи → `missing_locally`, сходимость; исчезнувшие свои ордера → resolved)
+ новые случаи: внешний ордер → `external_orders=1` без divergence и без
подбора в БД; внешний ордер из WS, исчезнувший с биржи → без
`missing_on_exchange`; ордер с пустым `clOrdId` → внешний. Все 66 unit-тестов
зелёные. Действующий прогон P1-72H не останавливался; правки вступят в силу
при следующем рестарте движка (текущий `divergences: 1` — исторический факт
нагрузочного теста, см. выше).

## Дополнение 2026-09-24: тест обрыва WS (P1-WSDROP)

**Сценарии и методика.**
1. **Unit** ([tests/test_ws_reconnect.py](../tests/test_ws_reconnect.py),
   фейковый OKX-сервер на loopback через `websockets.asyncio.server`, внешней
   сети нет): сервер обрывает соединение №1 кодом 1011 → клиент детектирует →
   reconnect → повторный login (private) → повтор всех подписок одним батчем →
   новый snapshot. Проверено: стакан инвалидируется сразу при обрыве
   (`get_book()` → None до нового snapshot); подписки восстанавливаются
   полностью (books+tickers+orders, 3/3 на обоих соединениях); login повторяется
   ровно один раз на новое соединение; `on_message` dispatch работает после
   reconnect; public-клиент переподключается без login; `notice 64008` закрывает
   сокет и включает reconnect без backoff; `_on_disconnect` сохраняет список
   подписок и сбрасывает ресинки. 4 новых теста, всего 70/70 OK.
2. **Живой прогон на demo** (`src/ws_drop_demo_run.py`, лог
   `logs/ws_drop_2026-09-24.log`): отдельные public и private клиенты,
   принудительное закрытие сокета (`close(1011)`) на живом соединении с
   дефолтной конфигурацией (backoff 5→60 с). Движок P1-72H не затрагивался:
   свои соединения, ордеров не выставлялось (внешний ордер зашумил бы
   `divergences` движка, работающего до рестарта на reconciler без RECON-EXT).

**Числа живого прогона (demo, 2026-09-24 04:38 +05):**

Побочное наблюдение: биржа прислала `channel-conn-count: 2` на канале orders —
второе соединение канала принадлежит движку P1-72H, косвенное подтверждение,
что его private WS жив (лимит 30 соед./канал далёк). После теста
`src.ops status`: `errors: 0`, `divergences` не изменился (1 — исторический).

**Потери сообщений.** Окно без данных ≈ 6.2 с; основной вклад —
`reconnect_delay` 5 с (дефолт боевой конфигурации, не тестовый костыль).
По темпу tickers (~3.6/с) пропущено ~20 сообщений tickers и все дельты books
за окно — это безопасно: новый snapshot полностью пересобирает стакан, дельты
разрыва не нужны. Для канала orders биржа пропущенные при разрыве сообщения
не доставляет — штатная компенсация: реконсилятор (сверка каждые 60 с) ловит
расхождения, а `divergences` движка — метрика именно этого риска.

**Найденный дефект (исправлен).** `ws_client.subscribe()/unsubscribe()` при
вызове до `connect()` падали с `AttributeError: module 'websockets' has no
attribute 'exceptions'`: websockets 17 не экспортирует подмодуль `exceptions`
лениво, а явного импорта не было. Дефект был латентным: движок подписывается
только после connect, а в unit-тестах подмодуль случайно импортировался
транзитивно. Пойман первым же живым прогоном `ws_drop_demo_run`. Фикс: явный
`import websockets.exceptions` в [src/ws_client.py](../src/ws_client.py).
Действующий движок работает на прежней версии модуля и подхватит фикс при
следующем рестарте; на него дефект не влияет (путь «subscribe до connect»
в движке не используется).

**Вывод.** Цепочка «разрыв → reconnect → login → повтор подписок → новый
snapshot» работает и в unit-симуляции, и вживую на demo: полное восстановление
~6 с при дефолтном backoff 5 с, состояние клиента и подписки не теряются,
стакан недоступен ровно до нового snapshot (anti-stale инвариант соблюдён).

## Дополнение 2026-09-24: тест rate limit (P1-RATELIMIT, `src/ratelimit_test.py`)

**Почему первый прогон (04:57) лимит не поймал.** Последовательные батчи 5×20 за 1636 мс ≈ 3 запроса/с — на два порядка ниже эндпоинт-лимита batch (~300 запросов/2с) и вдесятеро ниже суб-аккаунтного 1000 ордеров/2с. Лимит был недостижим по скорости, а не по счётчику.

**Решение.** Скрипт переписан на параллельный шторм: пул потоков, у каждого свой keep-alive exchange без throttler CCXT; ранняя остановка по Event; **backoff «под огнём»** — первый поймавший отказ воркер сразу делает retry-цикл, пока остальные держат окно насыщенным (иначе окно успевает сброситься и backoff проходит вхолостую). Режимы `--mode single|batch|public`, потолок ордеров режется по free-балансу (≤30%).

**Результат (прогон 05:17, `--mode single --threads 24 --linger-ms 5000`, лог `logs/ratelimit_single3_2026-09-24.log`, exit 0):**
- **50011 пойман** на `POST /trade/order` (BTC-USDT spot) на t=1470 мс: в окне до отказа прошло 116 запросов (115 принято). Повторный прогон (16 потоков) дал 117 за 1924 мс — числа воспроизводимы. Лимитер ведёт себя как token bucket ~60 + refill ~30/с; за linger-фазу зафиксировано 58 отказов 50011, пик ~189 запросов/2с.
- **Backoff отработал с реальным ретраем**: попытка 1 → 50011, пауза 0.5 с, попытка 2 → успех (t=2724 мс). `reject_codes=["50011"]`, `waits_s=[0.5]`.
- **Состояние не потеряно**: все счётчики возвращены в отчёт; 176 ордеров отменены batch-cancel + добивкой; висящих ордеров теста 0 (проверка `orders-pending` по префиксу `rt`); заголовков Retry-After/x-ratelimit у отказов нет.
- Контрольный public-прогон 05:11 (`logs/ratelimit_public_2026-09-24.log`): 50011 на `GET /market/ticker` после ~20–30 запросов/2с (по IP) — совпадает с документированными 20/2с.
- 50061 (суб-аккаунт 1000/2с) сознательно не провоцировался — см. okx-api.md §3.

**Влияние на движок (P1-72H).** `errors` 0 → 0, kill не активен, движок не останавливался. **НО** `divergences` 3 → 22: движок PID 24636 работает на коде до RECON-EXT и считает чужие ордера (префикс `rt`) рассинхроном. После рестарта на актуальном коде такие прогоны уйдут в метрику `external_orders` и divergences расти не будут. Это ожидаемое поведение старого кода, не повреждение состояния.

**Побочная находка.** В `src/errors.py` ERROR_MAP нет кода **50011** (есть 50061) — `explain_error("50011")` отдаёт fallback. Вынесено в задачу ERR-50011 (файл вне рамок P1-RATELIMIT).

**Вывод.** Лимит 50011 контролируемо воспроизводится на demo, backoff-механика проверена на живом отказе, числа задокументированы в okx-api.md §3. Для прод-клиента выводы: batch-place обходит per-order лимит места (считается по запросам), одиночный ретрай через 0.5 с обычно достаточен, под нагрузкой — экспоненциальный backoff с капом.

## Известные особенности

1. **checksum=0 и на demo, и на live** (проверено 2026-09-24 на `wspap` и `ws.okx.com`, канал `books`). Прежний вывод «на live будет полная валидация» неверен: единственная рабочая проверка целостности — цепочка `seqId`/`prevSeqId`.
2. **Websockets 17.1:** API изменился (нет `.closed`); клиент работает через try/except и `asyncio.wait`.
3. **`action` приходит**, но на верхнем уровне сообщения, а не внутри `data[]`. Прежний вывод «OKX не отправляет action» был ошибкой чтения; эвристика «snapshot = 100+ уровней» удалена.
4. **`expTime` — HTTP-заголовок**, а CCXT кладёт `params` в тело запроса (и одиночный ордер отправляет через `trade/batch-orders`). До исправления защита от «застрявших» ордеров не работала; теперь `OKXExchange.sign()` переносит его в заголовок.
5. **Ордера нативных grid-ботов** не видны в `orders-pending` — kill-switch останавливает ботов отдельно (`tradingBot/grid/stop-order-algo`, stopType 2 — монеты остаются). Вживую не проверялось, чтобы не остановить идущий grid-эксперимент ([grid-bot-demo-run.md](grid-bot-demo-run.md)).
6. **websockets 17:** `websockets.exceptions` — не ленивый атрибут пакета; без явного `import websockets.exceptions` обращение падает с `AttributeError`, если никто другой не импортировал подмодуль раньше (P1-WSDROP).
7. **Лимитер demo OKX — token bucket, а не жёсткое окно** (P1-RATELIMIT): `POST /trade/order` даёт 50011 только после ~115–117 запросов <2 с (при документированных 60/2с), одиночный ретрай через ~0.3–0.5 с проходит; `batch-orders` считается по запросам, а не по ордерам; заголовков `Retry-After` нет — паузы подбираем сами.
