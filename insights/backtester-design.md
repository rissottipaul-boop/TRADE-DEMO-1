### 0.1 Реализация (BT-IMPL) и отклонения от дизайна

Реализовано по §§1–6: `data` (history-candles → `market_data.db`, только `confirm=1`, gap-check, `dataset_id`), `engine` (open(t+1), «low раньше high», taker 0.10%×2 + 5 бп, tickSz/lotSz), `risk_sim` (тот же `src/risk.py`, модельное время, in-memory — `data/risk_state.db` не открывается), `walkforward` (180/30/30, шаг 30, holdout 182 д, purge/embargo), `metrics` (§6.1, гейт §6.2 — конфиг `GateConfig`), `analysis` (slicing/recursive), CLI `python -m src.backtest download|run|baseline`. Отклонения:

1. **Стоп при гэпе** исполняется от `min(open, stop)` минус проскальзывание, а не по цене стопа (§1.1 п.7) — консервативнее Freqtrade.
2. **Holdout** не трогают ни `run`, ни `baseline`, ни полнопериодные прогоны: гейт считается на конкатенации test-окон, holdout — только флагом `--touch-holdout`, каждое касание пишется в `holdout_touches` (§2.1 «одно касание»), отчёт выводит журнал. В журнале BTC-USDT уже 3 касания контрольных buy_hold/sma_cross: диагностика BT-IMPL до введения правила. Кандидатов (MEANREV и др.) это не затрагивает.
3. **Воспроизводимость:** кроме `dataset_id` снапшот фиксируют `--since/--until` + `--no-download` — хэш не позволяет выбрать диапазон, а база дописывается.
4. **Сегменты walk-forward независимы:** риск-ядро (breaker'ы, серии, блокировки) на границе окна обнуляется — в бою состояние непрерывно.
5. **Паритет риск-ядра включает его дефект:** `record_pnl` прибавляет PnL к equity (и к `day_pnl`), которую `update_equity` уже переоценил по рынку. HWM завышается, breaker −15% срабатывает раньше. В baseline: ETH SMA 50/200 in-sample — 2025-02-02 при истинной просадке 9.11%, дальше отклонён 31 вход. Бэктест повторяет боевое поведение, исправлять нужно в `risk.py` (задача на доске); на гейт WF не повлияло — в test-окнах breaker не срабатывал.
6. **Не реализовано в v1:** мультитаймфрейм и ресемплинг (§1.1 п.5–6), `--timeframe-detail` на 15m (§4.4), deflated Sharpe (§2.2 п.2 — отчёт даёт только число испытаний), сверка с Freqtrade (§5 п.4), чтение fee-tier (открытый вопрос 2). 15m/1D загрузчик качает (`--bar`), но в baseline не используются.
7. **Сайзинг спота** через `risk.size_position` — «контракт = 1 лот» (иначе `math.floor` округлил бы BTC до целых монет). Buy&hold — в рамках потолка позиции 15% equity; рынок (100%) — отдельной колонкой benchmark.
8. **Стресс slip×2** — кроме порога №1 §6.2, отчёт считает все 8 порогов при 10 бп (информативная колонка, §3.3).
9. **Recursive-проверка (§1.2) уточнена:** «на пересекающемся интервале сделки идентичны» недостижимо при путезависимом риск-оверлее: HWM breaker'а считается от старта прогона. Поэтому сделки сравниваются на интервалах, где совпадает состояние риск-ядра (`analysis._synced_intervals`). Расхождение состояния закрывает интервал и выводится в отчёт (на реальных данных — 3 эпизода `global_breaker`, сделки до них идентичны). Пустое сравнение (копии не синхронизировались или нет сделок) — «не проверено», не зелёный.

## 1. Anti-lookahead: как гарантируется

Lookahead bias — главный фальсификатор бэктестов: стратегия «видит» данные, которых в момент решения не существовало. Freqtrade прямо указывает: бэктестер загружает весь датафрейм целиком и считает индикаторы разом, поэтому неаккуратный код «подглядывает» вперёд, и именно bias обычно является причиной «too good to be true» результатов [И1].

### 1.1 Контракты движка (механические гарантии)

1. **Только подтверждённые свечи.** В расчёт входят только бары с `confirm == 1` (флаг OKX: `0` = свеча формируется, `1` = завершена [И4]). Формирующаяся свеча стратегии недоступна — движок её не отдаёт.
2. **Сигнал → исполнение на следующем баре.** Сигнал, вычисленный по закрытию свечи `t`, исполняется по цене **open свечи `t+1`**. Это же допущение Freqtrade: «Entries happen at open-price», «Exit-signal exits happen at open-price of the consecutive candle» [И2]. Запрет исполнения «по закрытию сигнальной свечи» — это скрытый lookahead (close известен только после закрытия).
3. **Прогрев индикаторов (startup period).** Первые `warmup = max_window * 2` баров периода отбрасываются из торговли (минимум — максимальное окно индикаторов стратегии; у Freqtrade это `startup_candle_count`, рекомендация ≥ 400 свечей при EMA100 [И2], [И6]).
4. **Запрет глобальных агрегатов.** Индикаторы — только через оконные функции (`rolling`), никаких `.mean()`/`.min()` по всему ряду, `shift(-N)`, `.iloc[-1]` внутри `populate_*` [И1], [И6].
5. **Мультитаймфрейм — только backward.** Слияние старшего ТФ с младшим — `merge_asof(direction='backward')` по времени **завершения** старшей свечи; forward-fill только прошлых значений, никогда будущих [И6].
6. **Ресемплинг:** агрегация с закрытием интервала справа (`label='right'`, `closed='right'`), чтобы метка свечи соответствовала моменту, когда она стала известна [И6].
7. **Консервативный порядок внутри свечи.** Внутри бара OHLC порядок high/low неизвестен → для стопов правило «**low раньше high**» (сначала худший сценарий), стоп исполняется по цене стопа даже если low ниже (это допущение Freqtrade; мы дополнительно накладываем проскальзывание, §3.3) [И2].
8. **Point-in-time данные.** Свечи OKX с `confirm=1` финальны; хранилище append-only, снапшот данных версионируется (§4.3) — повторный прогон на том же снапшоте обязан давать идентичный результат (воспроизводимость).

### 1.2 Валидационные прогоны (обязательные тесты BT-IMPL)

Аналоги инструментов Freqtrade, реализуемые как тесты движка:

- **Slicing-тест (аналог `lookahead-analysis`).** Прогон на полном ряде = baseline. Затем прогоны на усечённых префиксах (каждая точка входа/выхода как конец данных). Значения индикаторов и сигналы в пересечении обязаны совпадать побарно. Расхождение = bias [И1].
- **Recursive-тест (аналог `recursive-analysis`).** Прогоны с нарастающей датой старта; на пересекающемся интервале сделки идентичны. Ловит зависимость от стартовой точки и неявные глобальные статистики [И6].
- **NaN-guard:** ни одна сделка не может быть открыта на баре, где любой входной индикатор = NaN (незавершённый прогрев).

Источники: [И1] Freqtrade lookahead-analysis (механика baseline vs sliced, примеры bias: `shift(-10)`, `iloc`, глобальные агрегаты, `MACD(signalperiod=1)`); [И2] Freqtrade backtesting assumptions; [И6] spot-strategies.md §3 (anti-repainting практики, уже принятые в проекте); [И4] OKX candles (`confirm`).

## 2. Walk-forward: схема окон

**Зачем:** единичный прогон «оптимизация на всей истории → отчёт на ней же» = curve-fitting. Walk-forward оценивает, как параметры, выбранные на прошлом, работают на будущем, — единственная честная оценка перед paper-trading [И3], [И5].

### 2.1 Схема (стартовый дефолт)

```
|---- train 180d ----|-- valid 30d --|-- test 30d --|
                     |---- train 180d ----|-- valid 30d --|-- test 30d --|
                                         ...  (шаг 30 дней, окна катятся вперёд)
```

- **Rolling (скользящее) окно**, не expanding: crypto-режимы меняются быстро, старые данные теряют релевантность; rolling-окно — стандарт адаптации к смене режима. (Expanding-вариант `TimeSeriesSplit` из sklearn — референс реализации индексов; train всегда строго в прошлом относительно test [И3].)
- На **train** — перебор параметров; на **validation** — выбор одного набора (не подгонка под test!); на **test** — единственный прогон выбранного набора, его метрики идут в отчёт.
- **Финальный holdout:** последние 6 месяцев данных НЕ участвуют ни в одном окне до финальной приёмки стратегии — одно касание [И3] («знание о тестовой выборке протекает в модель через итерации»).
- **Отчётная метрика стратегии** — конкатенация OOS-участков (все test-окна + holdout), не train.

### 2.2 Ловушки (явно прописать в BT-IMPL)

1. **Перекрытие сделок через границу окна.** Сделка, открытая в train, закрывающаяся в test, размывает границу → **purge**: сделки, пересекающие границу, насильно закрываются на последнем баре train/valid и не попадают в test-статистику; плюс **embargo** = прогрев-окно индикаторов перед стартом каждого сегмента (переиспользуем warmup из §1.1.3). Концепция purged/embargoed CV — López de Prado [И5].
2. **Множественные сравнения.** Перебор N наборов параметров × K окон раздувает шанс «случайно красивого» результата → учитывать поправку на множественные проверки (deflated Sharpe / хотя бы честный подсчёт числа испытаний в отчёте) [И5].
3. **Режимное покрытие.** Окна обязаны покрывать разные режимы BTC (тренд/боковик/падение) — поэтому глубина истории §4.4 и запрет выбрасывать «неудобные» окна.
4. **Регулярные границы.** Месячный шаг совпадает с циклом «месячной ребалансировки» человеческих решений — не подгонять шаг под результат.

Источники: [И3] scikit-learn, «Cross validation of time series data» (TimeSeriesSplit: train — строго прошлое, классическая k-fold непригодна из-за автокорреляции; утечка знания о test через итерации подбора); [И5] López de Prado, *Advances in Financial Machine Learning*, гл. 7 (purging/embargo), гл. 11 (backtest overfitting); [И6] spot-strategies.md §2 (walk-forward как обязательная методология проекта).

## 3. Комиссии и проскальзывание OKX

### 3.1 Тарифы спота (официальная таблица okx.com/fees, снято 2026-09-24)

Tier считается от активов или 30-дневного объёма, применяется на следующий день; спот «Группа 1» (основные пары, включая BTC-USDT):

| Уровень | Условие (активы / объём 30д, USD) | Maker | Taker |
| --- | --- | --- | --- |
| **Базовый** | < 100k / < 1M | **0.0800%** | **0.1000%** |
| VIP 1 | ≥ 100k / ≥ 1M | 0.0675% | 0.0800% |
| VIP 2 | ≥ 200k / ≥ 5M | 0.0600% | 0.0700% |
| VIP 3 | ≥ 2M / ≥ 10M | 0.0550% | 0.0650% |
| VIP 4 | ≥ 5M / ≥ 20M | 0.0300% | 0.0450% |
| VIP 5 | ≥ 20M / ≥ 100M | 0.0250% | 0.0350% |

Независимое подтверждение порядка цифр: CoinMarketCap — «Trading fees on the platform start at 0.10%» (taker) [И8]. **Дефолт бэктестера — Базовый tier (0.08/0.10):** это наш реальный tier на старте live с минимальным капиталом; занижать комиссию «потому что может вырасти tier» запрещено (анти-оптимизм). Фактический tier аккаунта при переходе в live сверяется и подставляется в конфиг; если эндпоинт чтения fee-rate доступен — считывать, иначе держать базовый (консервативно).

**Механика в движке:** комиссия с каждого филла `fee = notional × rate`; комиссия списывается на входе И на выходе (как `--fee` у Freqtrade: «applied twice, on trade entry and exit» [И2]). Рыночные ордера — всегда taker. Лимитные: моделируем maker-исполнение **только если цена прошла сквозь лимит минимум на 1 тик** (touch = агрессивный сценарий taker — настраиваемо, дефолт консервативный taker); это защищает от завышения доли maker-филлов.

### 3.2 Округления

Цены — к `tickSz`, объёмы — `floor` к `lotSz`, минимум `minSz` из `GET /public/instruments` (снапшот параметров инструмента хранится вместе с данными; исторических изменений лимитов у нас нет — известное допущение, то же у Freqtrade [И2]).

### 3.3 Модель проскальзывания

Свечи OHLC не содержат стакана → параметрическая модель, консервативная:

```
exec_price(side=buy)  = ref_price × (1 + slippage_bps / 1e4)
exec_price(side=sell) = ref_price × (1 − slippage_bps / 1e4)
```

- `slippage_bps` — параметр конфига, **дефолт 5 бп на сторону** для BTC-USDT market-ордеров нашего размера (наш сайзинг — единицы-пары десятков USDT…сотни USDT, глубины top-of-book BTC-USDT хватает с большим запасом; 5 бп ≈ половина типичного спреда + запас).
- Стоп-лосс — всегда неблагоприятное проскальзывание (стоп срабатывает в движении против нас): `stop_price ∓ slippage`.
- **Правило 1000 мейкеров OKX** (остаток тейкер-ордера отменяется после матчинга с 1000 мейкерами [И7]) для наших размеров недостижимо — фиксируем как известное ограничение модели, не реализуем.
- **Калибровка:** среднее/max проскальзывание из задачи DEMO-SLIPPAGE (demo-стакан) — нижняя оценка; настоящая калибровка — на live-филлах Фазы 4 (еженедельный разбор «слиппедж vs бэктест» уже в roadmap). До калибровки все приёмочные метрики §6 считаются также при **удвоенном** проскальзывании (10 бп) — стресс-сценарий обязателен.
- **Чувствительность к комиссиям** — обязательный блок отчёта: результат при fee×0 (брутто), fee×1, fee×1.5 (на случай роста фактических издержек) [И6 §3].

## 4. Формат данных

### 4.1 Источник: REST-свечи OKX

| Параметр | `GET /api/v5/market/candles` | `GET /api/v5/market/history-candles` |
| --- | --- | --- |
| Покрытие | последние **1440** записей | история за годы (1s — только 3 мес) |
| Записей за запрос | max **300** (default 100) | max **300** (default 100) |
| Rate limit | **40 зап / 2с** | **20 зап / 2с** |
| Правило лимита | IP | IP |

Пагинация: `after` = записи **старше** ts, `before` = новее ts (итерируемся в прошлое через `after = ts самой старой свечи ответа`). Ответ — массив строк `[ts, o, h, l, c, vol, volCcy, volCcyQuote, confirm]`; `ts` — время **открытия** свечи в мс; `confirm=0` — незавершённая. Внимание: «первая свеча может быть неполной» и OHLC пустых периодов биржа достраивает предыдущим close (флаг `confirm` + vol=0 — маркер таких баров) [И4].

Оценка объёма загрузки: 2 года 1H = 17 520 баров ≈ 59 запросов ≈ **6 секунд** при соблюдении лимита. 1 год 15m = 35 040 баров ≈ 117 запросов ≈ 12 с. Тривиально.

### 4.2 Хранение: отдельная SQLite, та же техника, что `src/storage.py`

Решение: **отдельный файл `data/market_data.db`**, не `bot_state.db`. Причины: рыночные данные — большой append-only массив, не часть операционного состояния движка; бэктест читает его read-only; не смешиваем жизненные циклы (state живёт/мигрирует с движком, данные — накапливаются). Стиль схемы — как в `src/storage.py` (явный PK, индексы, сырые значения TEXT/REAL):

```sql
CREATE TABLE IF NOT EXISTS candles (
    inst_id TEXT NOT NULL,
    bar     TEXT NOT NULL,          -- '15m','1H','4H','1Dutc'...
    ts      INTEGER NOT NULL,       -- open time, ms (UTC)
    o REAL NOT NULL, h REAL NOT NULL, l REAL NOT NULL, c REAL NOT NULL,
    vol REAL, vol_ccy REAL, vol_ccy_quote REAL,
    confirm INTEGER NOT NULL,       -- 1 = финальная
    PRIMARY KEY (inst_id, bar, ts)
);
CREATE INDEX IF NOT EXISTS idx_candles_ts ON candles(inst_id, bar, ts);
```

Свечи биржи храним **в строковом виде тоже** (поле `raw` опционально) — для расследования расхождений; числа REAL достаточны для бэктеста, но `raw` даёт аудит.

### 4.3 Контроль целостности (загрузчик BT-IMPL)

1. **Gap-check:** непрерывность `ts` с шагом бара; пропуски → список дыр в отчёт загрузки (свечи без сделок биржа отдаёт с подставленным close — это НЕ дыра, vol=0 легитимен).
2. **Только `confirm=1`** пишутся как финальные; `confirm=0` никогда не попадает в датасет бэктеста.
3. **Снапшот версионируется:** директория/тег датасета (`dataset_id` в мета-таблице: источник, дата выгрузки, диапазон, хэш) → воспроизводимость прогонов и честный holdout.
4. Дедупликация по PK при повторной докачке; верхний край обрезаем до последней завершённой свечи.

### 4.4 Требуемая глубина истории

| Таймфрейм | Глубина | Зачем |
| --- | --- | --- |
| **1H** (рабочий для сигнальных стратегий Фазы 2) | **≥ 2 года** | покрытие разных режимов BTC (тренд/боковик/пролив) — требование §2.2.3; ~17.5k баров |
| **15m** (detail-таймфрейм для внутрибарной точности, аналог `--timeframe-detail` [И2]) | 6–12 мес | уточнение исполнения стопов/тейков внутри 1H-бара |
| **1D** | ≥ 2 года | контекстные фильтры старшего ТФ |
| 1m | не качаем в v1 | объём ×1440 против 1H без пользы для наших стратегий |

Спот-свечи OKX — без ограничений глубины по годам (в отличие от MARK-свечей SWAP ~3 мес [И7]) — ещё один аргумент за спот-первую фазу.

**Рекомендация: свой лёгкий событийный движок**, потому что:

1. **Паритет риска и исполнения** — главный аргумент. У нас уже есть риск-ядро с недетерминированной логикой breaker'ов ([risk-core.md](risk-core.md)) и живой движок Фазы 1. Чужой бэктестер = вторая модель исполнения и второй риск — расхождение «бэктест vs демо» становится неотлаживаемым.
2. Наши первые стратегии — **state-машины** (DCA IDLE→BUYING→COOLDOWN, grid-лестница), а не векторные сигналы: vectorbt/freqtrade-модель им не соответствует, Jesse не умеет OKX-спот.
3. Объём работ мал: цикл по барам + симуляция филлов по правилам §1/§3 + метрики §6. Спецификация исполнения уже формально описана — допущениями Freqtrade [И2], мы их копируем с ужесточением (slippage, консервативный taker).
4. **Freqtrade остаётся в проекте как эталон:** (а) спецификация допущений и валидационных тестов; (б) опционально в BT-IMPL — порт RSI/BB-стратегии во Freqtrade и сверка сделок с нашим движком на одном датасете (перекрёстная проверка, расхождение = баг у кого-то из двух).
5. vectorbt — допустим как **офлайн-инструмент исследований** (быстрые параметрические свипы индикаторов в ноутбуке), не как движок приёмки: walk-forward и limit-ордера — платные PRO-фичи, лицензия Commons Clause, паритета с live не даёт [И9].

Источники: [И1], [И2] Freqtrade docs; [И7] okx-api.md §7; [И9] github.com/polakowo/vectorbt (README, docs/getting-started/upgrade.md, LICENSE.md); [И10] github.com/jesse-ai/jesse (`jesse/info.py` — таблица бирж и флаги `backtesting`).

## 6. Метрики результата и пороги приёмки

### 6.1 Что считает движок (обязательный набор отчёта)

Определения совместимы с Freqtrade summary metrics [И2] и риск-ядром [И11]:

| Метрика | Определение |
| --- | --- |
| Total/Net profit | абсолют и % от стартового капитала, после комиссий и проскальзывания |
| **CAGR** | годовая скорость роста equity |
| **Max Drawdown (MDD)** | макс. просадка от high-water mark, % и длительность; считается по **wallet balance** (вкл. нереализованный PnL), не только по закрытым сделкам |
| **Sharpe / Sortino** | годовые, по дневным доходностям wallet balance (annualization = 365 для крипты); Sortino — по downside-отклонению |
| Calmar | CAGR / MDD |
| **Hit rate (win%)** | доля прибыльных сделок |
| **Expectancy** | средний PnL на сделку (% и USDT) = hit_rate × avg_win − (1−hit_rate) × avg_loss |
| **Profit factor** | сумма прибылей / сумма убытков |
| Сделок / длительность | число закрытых сделок, avg/min/max длительность, max серия убытков подряд |
| **Издержки** | сумма комиссий и смоделированного проскальзывания; доля в брутто-прибыли |
| Breakdown | по месяцам/годам и по walk-forward окнам |
| vs Buy&Hold | изменение рынка за период (benchmark) |

### 6.2 Пороги приёмки стратегии (стартовые дефолты; калибруются в RISK-CALIB)

Стратегия допускается к paper/dry-run (критерий выхода Фазы 2), только если на **OOS-конкатенации walk-forward** одновременно:

| # | Порог | Обоснование |
| --- | --- | --- |
| 1 | **Expectancy > 0** после комиссий и при **удвоенном** проскальзывании | стресс-устойчивость к ошибке модели издержек (§3.3) |
| 2 | **Profit factor ≥ 1.3** | ниже — сигнал в пределах шума издержек (fee 0.2% на круг съедает тонкий edge) |
| 3 | **Sharpe (OOS) ≥ 0.5** | скромный порог для крипто-шума; растёт через RISK-CALIB |
| 4 | **MDD(OOS, wallet) ≤ 10%** | буфер под глобальный breaker риск-ядра −15% [И11]: бэктест-MDD × 1.5 не должен сносить breaker в бою |
| 5 | **≥ 100 закрытых сделок** суммарно на OOS (и ≥ 30 на окно для оконных выводов) | статистическая осмысленность hit rate/expectancy |
| 6 | **Прибыльных test-окон ≥ 60%** | устойчивость к режимам; одно сверхокно не протаскивает стратегию |
| 7 | Доля комиссий+проскальзывания в брутто-PnL **< 50%** | иначе стратегия кормит биржу, а не нас [И6 §3] |
| 8 | Макс. серия убытков OOS **≤ 7** | согласованность с риск-ядром (системная пауза после 5 — стратегия не должна штатно в неё упираться [И11]) |

Любой порог не пройден → стратегия в доработку, не в paper. Пороги — конфиг, не константы кода.
