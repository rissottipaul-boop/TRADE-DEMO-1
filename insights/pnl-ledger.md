# Учёт PnL по рукавам (PNL-LEDGER): методика и запуск

- **Дата:** 2026-09-24
- **Тема:** как `src/pnl_ledger.py` считает PnL по рукавам [business-plan.md](business-plan.md) §2.1: источники, атрибуция, формулы, сверка, отчёт
- **Статус:** validated по коду, тестам и demo. `tests/test_pnl_ledger.py` — 60 тестов на фейковых ответах OKX. Сверка с `totalEq` по индексам и атрибуция исполнений без algoId (PNL-RECON-DRIFT) проверены на demo 03.10, см. §4. Факты о demo в §1 проверил автор модуля 24.09, они записаны в docstring модуля; 24.09 в 11:4x облачная сессия их не перепроверяла — нет ключа и сети до OKX. Первый прогон на demo — остаток задачи PNL-LEDGER.
- **Решение, которое принимается:** откуда брать цифры для ежедневного отчёта, еженедельного разбора (LIVE-REVIEW, [business-plan.md](business-plan.md) §6 п. 2–3) и трека для copy trading

> Отчёт — учёт, а не прогноз. Не финансовый совет.

## 0. Запуск

```
python -m src.pnl_ledger                              # demo, сегодня (+05:00) -> data/reports/
python -m src.pnl_ledger --date 2026-09-24            # конкретный день
python -m src.pnl_ledger --mode live --date 2026-09-30 --days 7   # неделя live-кармана для LIVE-REVIEW
python -m src.pnl_ledger --telegram                   # + текст сообщения (отправит ALERTS-IMPL)
python -m src.pnl_ledger --no-save                    # без файлов отчёта (журнал всё равно обновится)
```

- **Коды выхода:** 0 — отчёт без предупреждений, 1 — есть предупреждения (раздел «Предупреждения» отчёта), 2 — отчёт не построен (правила, период, биржа).
- **Файлы:** `<каталог режима>/reports/pnl_<день>.md` и `.json`; у периода имя `pnl_<первый>_<последний>`. Каталог режима — `data/` для demo и `data/live/` для live (`config.state_paths`).
- **Журнал** `<каталог режима>/reports/pnl_ledger.db` хранит bills, ордера ботов и снимки equity. Биржа отдаёт bills за 7 дней, архив — за 3 месяца. Если запускать ledger реже раза в 3 месяца, старая история пропадёт.
- **Только чтение.** `Reader` пропускает только вызовы `private_get_*` и `public_get_*`; любой другой метод — `ValueError` до обращения к бирже (тест `ReaderTest`). База движка `bot_state.db` открывается с `mode=ro`, отсутствующую базу ledger не создаёт.

Факты о demo 24.09 из docstring модуля (в этой сессии не перепроверялись):

- сумма `balChg` по валюте с начала истории равна `eq` торгового счёта;
- исполнения нативных ботов в bills есть, а в `trade/fills` их нет;
- комиссия уже внутри `balChg`;

Это сходится с [okx-api.md](okx-api.md) §10 п. 19–20: ордера ботов не видны в `orders-pending` и `orders-history`, поэтому ordId ботов берутся только из bot API.

## 2. Атрибуция по рукавам

Правила — `ops/sleeves.json` (не периметр guard, правят агенты). При запуске файл проверяется: ссылка на неописанный рукав или неизвестный режим — отчёт не строится (код 2). Тест `RulesTest.test_every_registered_owner_has_a_sleeve` требует строку для каждого кода реестра `src/order_owner.py`.

Порядок для каждого bill:

1. **Перевод капитала** — `type 1` (между счетами) и `type 12` (в бота и из бота): вне рукавов, раздел «Вне рукавов».
2. **Funding** — `type 8`: `funding.by_inst[instId]`, иначе `funding.default_sleeve` (`funding_carry`).
3. **Проценты по займу** — `type 7`: `default_sleeve` с источником `interest:<ccy>`. За период такие bills дают предупреждение — на счёте был заём (autoLoan, см. SPOT-TDMODE).
4. **Исполнение нативного бота** — `ordId` есть среди ордеров ботов. Рукав: `bots[algoId]` → `bot_algo_cl_ord_id_prefixes[префикс algoClOrdId]` → владелец `algoClOrdId` по реестру → иначе `default_sleeve` и предупреждение «боты без правила».
   - `clOrdId` вида `O` + 19 цифр без `ordId` в журнале. Такой `clOrdId` OKX даёт не только ботам, но и любому системному ордеру: закрытию остатка при остановке бота и сработавшему TP/SL или OCO агента (у них `tag` = `CLI`). Порядок (PNL-RECON-DRIFT, 03.10):
     1. бот по `instId` и времени жизни (±10 мин); если кандидатов несколько — бот, остановившийся ближе всего к исполнению;
     2. иначе владелец открытой спот-позиции по `instId`, которую исполнение уменьшает. Если таких владельцев несколько, выбирается тот, у кого исполнение свежее. Пример: OCO-стоп памп-кармана уходит к `clOrdId:pmp`;
     3. иначе — `default_sleeve` и предупреждение.

     Решение кэшируется по `ordId`, поэтому обе ноги и все части ордера уходят одному владельцу.
5. **Владелец по `clOrdId`** — код реестра `src/order_owner.py`, если у него есть рукав; иначе самый длинный префикс таблицы `cl_ord_id_prefixes`. Таблица режима перекрывает общую `*`: в demo `bot`/`botr` — рукав `engine`, в live — `dca` (там `bot*` ставит только `src.live_runner`).
6. **`tag`** — таблица `tags`: в demo `CLI`/`MCP` — `agent_cli`, brokerId CCXT `6b9ad766b55dBCDE` — `tests`.
7. **Остальное** — `default_sleeve` (`manual`, «Прочее / ручное»): без `clOrdId` и `tag` — «вероятно, ордер человека»; незнакомый `type` — предупреждение. Ничего не выбрасывается.
8. **Обмен стартовых активов человеком.** Исполнение без `clOrdId` и `tag` может целиком продать актив, который лежит «вне рукавов» (24.09: 100 стартовых OKB). Такое исполнение считается обменом внутри «вне рукавов», а не позицией «Прочее / ручное». Иначе «ручное» держало бы шорт OKB, а «вне рукавов» — те же OKB в лонг, и обе строки каждый день переоценивались бы навстречу друг другу. 02.10 так вышло +81 USDT в «ручном» без единой сделки. Результат обмена за период входит в переоценку «вне рукавов» по ценам конца, поле `unallocated.conversions`. Покупка и продажа сверх пула остаются в «Прочее / ручное».

Начисления Earn идут в `earn_sleeve` (`cash_earn`): в bills торгового счёта их нет.

## 3. Формулы

- **Период** — календарные дни в поясе `--tz` (по умолчанию +05:00): `[первый день 00:00, последний день + 1 00:00)`. Момент оценки `t1 = min(конец, сейчас)`; текущий день помечен «неполный».
- **Книга** — движения одного источника внутри рукава (бот, префикс `clOrdId`, `tag`, funding…). Остаток книги `h(t)` = Σ `balChg` по валютам до момента `t`.
- **PnL рукава** = `V(t1) − V(t0)`, где `V(t) = Σ h_ccy(t) × цена_ccy(t)` в USDT, плюс Earn. Это mark-to-market: в нём уже реализованный и нереализованный результат, комиссии и funding.
- **Реализованный** — по средней цене позиции `instId` внутри книги. Исполнение — две ноги (база и котируемая) с общими `instId`, `tradeId` и `ordId`. Реализовано = `(цена − средняя) × закрытое количество`; при перевороте остаток открывает новую позицию по цене исполнения. Позиции строятся по всей истории журнала, в отчёт попадает только результат периода.
- **Δ нереализованного** = PnL торговли − реализованный − funding − проценты − прочее.
- **Комиссии** — справочная колонка: они уже внутри PnL. В bills `fee < 0` — списание.
- **Вложено** — себестоимость long-позиций кода плюс `investment` работающих ботов из bot API.
- **Боты** — сверка с биржей: PnL ledger = `V(t1)` всех движений бота с начала журнала, рядом `totalPnl` OKX и разница. Разница показывает, что часть истории бота старше журнала или биржа считает иначе.
- **Остатки до начала журнала** = `eq − Σ balChg` журнала. Если не ноль — заметка «история bills не с начала счёта», эти остатки идут во «Вне рукавов» и переоцениваются.

## 4. Сверка

1. **Тождество модели:** Δ стоимости торгового счёта = Σ PnL торговли рукавов + переоценка активов вне рукавов + переводы капитала. Выполняется по построению; ошибка больше 0.01 USDT — предупреждение, обычно из-за цен.
2. **Уровень на конец** (только текущий период): модель против `asset-valuation` `trading`.
3. **Снимки биржи:** эталон — самый ранний снимок внутри периода, согласованный с моделью (≤ 5%; предварительный отсев — 10% по текущим ценам). Снимки ledger — в USDT; `equity_curve` движка в demo — `totalEq` в USD, пересчёт по индексу `USDT-USD`; в live runner пишет USDT. Конец — `asset-valuation` сейчас (текущий период) или последний согласованный снимок. **Модель в каждой точке оценивается ценами источника снимка:** снимок в USD (`totalEq`) — индексами `<ccy>-USD`, снимок в USDT (`asset-valuation`) — ценами спота. Невязка = Δ биржи − Δ модели; **больше 0.2% equity — предупреждение (код выхода 1).** Отдельной строкой отчёт показывает «цены demo-спота против индекса» (`price_basis_usdt`) и невязку по споту (`residual_spot_usdt`) — прежнюю метрику.
4. **Просадка по снимкам** одного источника — для LIVE-REVIEW §6 п. 3.

Источники невязки: цены (тикер против минутной свечи с интерполяцией), время снимков и балансы вне bills — например, нереализованный PnL открытых SWAP-позиций (§5 п. 3).

**Разбор PNL-RECON-DRIFT (03.10): растущая невязка 30.09–02.10 — это цены, а не потерянные движения.**

- **Факт 1 (demo 03.10 05:1x, `account/balance` и `market/index-tickers`).** По каждой валюте `eqUsd / eq` = `idxPx` индекса `<ccy>-USD`, а сумма `eqUsd` = `totalEq`. Например, BTC: 84 461.1 и 84 461.1, ETH: 2 665.21 и 2 665.21. Значит, `totalEq`, который пишет движок, оценён глобальным индексом, а не ценами demo-рынка.
- **Факт 2 (минутные свечи demo, спот против индекса).** Цена demo-спота BTC-USDT ушла от индекса: 24.09 — +0.0%; 02.10 00:00 — 85 186.9 при BTC-USD/USDT-USD = 84 843.6 (+343); 02.10 23:58 — 85 459.8 при 84 302.7 (+1 157). На счёте около 1 BTC стартовых активов, поэтому эта разница целиком попадала в невязку: −334 → −1 150 по уровню, −816 за день. Цены ETH, OKB и альткоинов от индекса почти не отличаются.
- **Факт 3 (`asset-valuation`).** `trading` = 109 987.58 при модели по споту 109 969.38 и `totalEq`/`USDT-USD` 109 273.99. `asset-valuation` оценивает по ценам demo-спота, поэтому его снимки сверяются со спотовой моделью.
- **После исправления** — отчёты пересчитаны 03.10. Невязка в ценах источника: 30.09 −8.30 USDT (−0.008%), 01.10 −22.86 (−0.021%), 02.10 +7.67 (+0.007%). Разница цен спота и индекса за те же отрезки: +66.87 / −167.68 / −823.88; невязка по споту прежняя: +58.56 / −190.54 / −816.21. Тождество модели — до 1e-06, предупреждений нет.
- **Атрибуция за те же дни.** «Прочее / ручное» = 0.00 все три дня. Памп: −3.17 / −10.00 / −3.35; в старом отчёте за 02.10 было −115.33 при `bot:?` +111.83 — это была одна позиция HYPE, разорванная на две книги. Демо-флот: +9.37 / +36.77 / −75.26.
- **Сверка с PnL ботов.** В отчёте за прошлый день `totalPnl` OKX взят на момент формирования отчёта, а PnL ledger — на конец дня. Отсюда разница −0.6…−23.7 USDT. В одной точке времени (03.10 05:2x) она по работающим ботам от −3.07 до +0.42 USDT. Таблица ботов в отчёте теперь об этом предупреждает.

## 5. Ограничения и открытые вопросы

1. **Earn в demo недоступен** (50038): рукав `cash_earn` в demo пуст. Работает ли `lending-history` на live-суб-аккаунте — HUNT-EARN-SUBACCT.
2. **Цены.** Для валюты без пары к USDT, USDC, BTC или ETH цена 0 и предупреждение. Прошлые моменты — минутные свечи, по запросу на валюту и минуту.
3. **Деривативы.** Для не-спотовых исполнений реализованный — это кэш-ноги; открытые SWAP-позиции по mark не переоцениваются, в bills их нереализованного PnL нет. До CARRY-IMPL и RISK-FUNDING-PNL рукав carry виден только через funding и закрытия.
4. **Режим `acctLv=3`** (incidents.md 10:10): поля bills для спота с `tdMode=cross` на demo не проверены.
5. **Первый прогон на demo проверен (30.09)** — отчёт за 24.09 сформирован (`data/reports/pnl_2026-09-24.md` и `.json`): 886 сделок, PnL рукавов +69.49 USDT (демо-флот +120.56, памп +19.55, нативный grid +0.46, manual -60.92, CLI -10.60), комиссии 47.30 USDT. Тождество модели выполнено (ошибка 4.4e-07); переводы капитала (+5 000 USDT) корректно изолированы от PnL; невязка со снимками биржи всего +32.90 USDT (0.03157% equity); PnL BTC-grid +0.46 USDT (OKX totalPnl -0.16 USDT, разница +0.62 объясняется mark-to-market ценой остатка базы). Все 15 ботов сверены. Задача `PNL-LEDGER` закрыта.
