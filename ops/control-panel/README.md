# Контур — локальная панель проекта

## Задачи, результаты и качество AI (21–30, 39–48)

«Помощник» готовит локальный черновик с критерием и ролью; доска меняется только штатным циклом агента. В карточке задачи доступны полный handoff и проверка Git diff с ограничениями и замечаниями для рецензента.

События выбранного запуска дополняются по курсору каждые 3 секунды. Результат показывает заявленные файлы, проверки, внешние IDs, следующий шаг и недостающие доказательства. Контекст для продолжения возвращает пакет задачи, `session_resumed=false`: внешняя сессия не возобновляется без подтверждённого протокола. Resume/cancel/steer отображаются только при поддержке адаптером. Кодовые HTTP-запуски Insight Executor требуют worktree от чистого checkout.

«Работа AI» показывает reported/unknown стоимость, фактические вызовы инструментов и серверную задержку. Встроенные сценарии — offline-фикстуры; сохранённые ответы реальной модели сравниваются через `python -m src.ai_evals compare`.

| Метод | Путь | Содержание |
| --- | --- | --- |
| POST | `/api/assistant/draft` | `{description}` → Markdown черновика, роль и критерий |
| POST | `/api/assistant/review` | `{task_id, run_id?}` → diff, источники и findings |
| POST | `/api/assistant/tool` | `{name, arguments}` → закрытый read-only инструмент |
| GET | `/api/run/result?id=<run_id>` | Результат с reported/unknown provenance |
| GET | `/api/run/context?id=<run_id>` | Полный handoff, `session_resumed=false` |
| GET | `/api/ai/observability` | USD, модели, задержки, ошибки, безопасный журнал |
| GET | `/api/ai/evals` | 11 локальных контрольных проверок |

Маршруты защищены токеном, Host и Origin; неизвестные поля, типы и диапазоны отвергаются до исполнения. Shell, торговля, запись доски и управление процессами отсутствуют в AI allowlist. Подробности и границы приёмки — [insights/agent-ai-workflows.md](../../insights/agent-ai-workflows.md).

Старт из корня проекта:

```powershell
.venv\Scripts\python.exe -m src.control_panel
```

Команда печатает ссылку с временным токеном. Откройте её в браузере на этом компьютере. По умолчанию панель слушает `127.0.0.1:8765`; `--port 0` выбирает свободный порт. Остановить панель — `Ctrl+C`. Токен меняется при каждом запуске, не записывается в файл и не выводится в access log.

## Фоновый запуск

Скрипт `ops/panel.ps1` (запуск через `src/control_panel_boot.py`) поднимает ту же панель фоном. Команды выполняются из корня проекта:

```powershell
ops\panel.ps1 start                # запуск фоном (по умолчанию порт 8765)
ops\panel.ps1 status               # проверка: процесс этой копии + /health
ops\panel.ps1 stop                 # остановка только подтверждённых процессов этой копии
ops\panel.ps1 restart              # stop + start
ops\panel.ps1 open                 # если не запущена — запустить, затем открыть ссылку в браузере
ops\panel.ps1 url                  # ссылка с замаскированным токеном
ops\panel.ps1 url -ShowToken       # полная ссылка с токеном
```

У `start` есть необязательные параметры `-Port 8765` и `-Token <t>` (свой токен: 22–128 символов `[A-Za-z0-9_-]`). Успехом `start` считается только ответ `/health` от процесса, который скрипт сам запустил и подтвердил по слушателю порта. Свой процесс скрипт узнаёт по связке PID + время создания процесса + одноразовая метка запуска (`nonce`) в командной строке; чужой процесс на том же PID или порту не трогает, а просит выбрать другой `-Port`.

Защита токена (DPAPI): токен новый на каждый запуск и хранится только в `data\control_panel_token.dpapi`, зашифрованном DPAPI текущего пользователя (формат `ConvertFrom-SecureString`). Расшифровывает его сам `src/control_panel_boot.py`; в командной строке токена нет. Скрипт токен не печатает: `url` показывает маску `?token=<скрыт>`, целиком — только с явным `-ShowToken`; `open` передаёт полную ссылку напрямую браузеру. Вывод сервера уходит в никуда (`os.devnull`), ошибки — в `logs\control-panel.log`; старые ссылки с токеном в логе при показе маскируются. Устаревший файл с открытым токеном `data\control_panel_token.txt` скрипт удаляет при `start`/`stop`.

Коды выхода `status`: `0` — панель здорова (процесс этой копии жив, порт слушают только свои процессы, `/health` отвечает `ok`); `1` — ошибка (не запущена, не отвечает или порт занят чужой копией). `start`/`stop`/`restart`/`open`/`url` возвращают `0` при успехе и `1` при ошибке тем же порядком.

## Что показывает

- Все строки `ops/board.md` с поиском и фильтрами; дубликаты ID отмечаются. По клику на ID открывается полный критерий, зависимости и заметки. Число доступных задач учитывает выполненные зависимости и неоднозначные ID. Панель не меняет доску и не переносит решения человека.
- Рантаймы и назначенные модели из `ops/agent-routing.json`; события запуска из `logs/agent-rotate.log`.
- Для каждого рантайма показаны состояние допуска к запуску и число отказов guard с его `client` в последних 64 КиБ `data/guard.log`. Счётчик не является подтверждением E2E: старые записи без `client` и строки за пределами хвоста не учитываются. Команды, причины отказов и фрагменты журнала не передаются в браузер.
- В карточке задачи можно получить план `agent-rotate.ps1 -Plan`: выбранный рантайм, доступность CLI, модель и состояние guard. Этот просмотр не создаёт run, claim или запись в журнале ротации.
- Кнопка «Сформировать пакет» создаёт текст для передачи задачи другому рантайму: полная строка доски, зависимости, все активные claims, SHA256 доски, Git HEAD/ветка/имена изменений и записи ротации с тем же ID задачи. Пакет создаётся на момент запроса и копируется через буфер обмена; типичные значения ключей и токенов скрываются. Он не создаёт claim и не заменяет новый SYNC, сверку Git и внешних действий.
- Состояние движка через `src.engine_watchdog` и риск через существующий `src.obsidian_status.build_snapshot`.
- Очередь Muse: последние заявки `inbox`, `processing` и `outbox` с фильтром стадий, ID, ролью, источником и путём записи. `processing` означает только наличие файла, а не доказанный живой процесс; стоимость помечена как неизвестная. Prompt, ошибки и вывод модели не передаются в браузер.
- Единый обзор claims доски и наблюдаемых запусков: локальные записи `data/runs/` и заявки Muse из файловой очереди. Каждая строка показывает источник и качество статуса; claim не считается доказательством живого процесса, а `processing` Muse остаётся файловой стадией. События лаунчера (`start`/`finish` с кодом выхода) переносятся в запись по `run_id` из журнала ротации; `finish` делает статус `completed`/`failed` с качеством `exit-code-only` — код выхода не подтверждает критерий доски. Для Claude и Codex при однозначной привязке (единственная сессия по каталогу запуска и окну времени) события дополняются из нативных журналов сессий (`~/.claude/projects/...jsonl`, `~/.codex/sessions/...rollout-*.jsonl`) с качеством `native` и provenance-путём; копируются только метаданные (время, тип, модель, числа usage) — текст prompt и вывода в запись не попадает. Если процесс исчез без записи `finish`, статус становится `unknown`; повтор разблокируется только после сверки (в том числе автоматической — по появившейся записи `finish`). Стоимость — всегда с полями `quality` и `provenance`: у Claude берётся фактический `costUSD` из `cost-state` файла сессии (`reported`); журнал Codex содержит только токены (они показываются отдельно), у Gemini и Muse источника нет — честно `unknown` с причиной. `GET /api/capabilities` показывает доступные операции для каждого рантайма и provenance их подтверждения.
- Известные PID-файлы движка, live-runner и Muse, а также `git worktree list`. Для PID-файлов показано наличие процесса; владельца подтверждает только профильная ops-команда.
- Lease рабочих копий из `data/worktree-leases/`: задача, run ID, ветка, базовый commit, возраст heartbeat и проверка регистрации через Git. Пока процесс запуска жив, панель продлевает heartbeat активного lease (не чаще раза в минуту); мёртвый процесс heartbeat не продлевает, и lease честно стареет — stale-детект требует сверки, но не освобождает lease автоматически. Новая копия создаётся `src.worktree_lease.prepare_worktree` только из чистого HEAD, с атомарным резервированием задачи. `POST /api/runs` с `"workspace":"worktree"` связывает lease с запуском: агент стартует внутри изолированной копии, а по записи `finish` лаунчера lease помечается `released` — сам worktree и ветка остаются для ручной сверки diff, автоматического merge нет.
- Короткие хвосты логов движка и делегирования.

Обновление — каждые 10 секунд. Часть данных может быть недоступна, если соответствующий файл ещё не создан; остальные разделы продолжат работать.

## Кнопки

Разрешены `engine.start`, `engine.stop`, `delegation.pause`, `delegation.stop`. Движком и раннером управляют уже существующие `ops/engine.ps1` и `ops/delegate.ps1`; панель не завершает процессы по PID сама. Каждое действие требует подтверждения в браузере. `delegation.pause` создаёт `ops/delegations/PAUSED` и не удаляет заявки.

Результат каждого HTTP-действия записывается в `logs/control-panel-actions.jsonl` без токена, prompt и вывода команды.

`POST /api/runs` запускает CLI только при подтверждённом E2E guard конкретного клиента, доступном CLI и готовой задаче. Подтверждение — `guard_status: e2e-verified` в `ops/agent-routing.json` плюс файл `ops/hooks/launch-e2e.json` вида `{"schema_version":1,"clients":{"codex":{"verified":true}}}` (создан 03.10 решением человека для всех четырёх клиентов). Эти файлы защищены правилами [AGENTS.md](../../AGENTS.md) §2; оператор обновляет их только после E2E. Панель передаёт лаунчеру `-RunId` — корреляционный ID записи `data/runs/`, по которому события журнала ротации попадают в запись запуска; в prompt клиента он не входит.

`POST /api/run/cancel` и `POST /api/run/steer` отвечают `unsupported`: ни один клиент не заявил в матрице capabilities подтверждённый протокол отмены/вмешательства в сессию, а PID не подтверждает владение процессом, поэтому панель не завершает процессы и не имитирует успех. Возобновление очереди, reset блокировок и торговые операции недоступны. Текущие возможности и дальнейший контракт описаны в [архитектуре](../agent-control-plane.md).

## HTTP

- `GET /health` — минимальный статус сервера.
- `GET /api/state` — агрегированный снимок, заголовок `X-Control-Token`.
- `GET /api/capabilities` — возможности рантаймов после проверки guard и provenance их подтверждения.
- `GET /api/runs` — краткая проекция локальных запусков вместе с наблюдаемыми заявками Muse; внутренние поля и события локальной записи в общий список не попадают. `managed: false` и `state_quality: file-stage` отличают файловую заявку от управляемой сессии.
- `GET /api/worktree-leases` — записи lease и признак регистрации worktree, без вывода о владельце процесса.
- `GET /api/run/events?id=run_ID&after=0` — события локального запуска после курсора; ответ содержит `next_cursor` и `has_more`. Для файловых заявок Muse клиентский event log пока недоступен, поэтому этот путь не выдаёт вымышленные события. В панели видны тип, время и курсор события; сырой вывод модели не показывается.
- `GET /api/task?id=ID` — полная карточка; дубликаты ID отклоняются.
- `GET /api/handoff?id=ID` — снимок передачи и Markdown для копирования; токен обязателен, дубликаты ID отклоняются. Читает доску, `git status` и журнал ротации, не читает `.env` или содержимое diff.
- `POST /api/agent/plan` — JSON `{"task_id":"ID","role":"insight-executor","agent":"auto"}`; вызывает только `-Plan`, возвращает отфильтрованный результат без prompt и CLI-аргументов.
- `POST /api/runs` — запуск готовой задачи после той же проверки, что в плане; неизвестный итог предыдущего запуска блокирует повтор до сверки. Поле `"workspace":"worktree"` даёт изолированную копию с lease; по умолчанию `checkout`.
- `POST /api/run/cancel` — явный ответ `unsupported`, пока клиент не заявил подтверждённую отмену в матрице capabilities; PID не завершается.
- `POST /api/run/steer` — явный ответ `unsupported` по той же причине; инструкция не сохраняется и не передаётся.
- `POST /api/action` — JSON `{"action":"engine.stop"}` и тот же заголовок.

Сервер принимает только `Host: 127.0.0.1:<порт>`, проверяет `Origin` для POST, ограничивает размер тела запроса и допускает только перечисленные действия. Панель предназначена для доверенного локального компьютера. Не публикуйте порт через reverse proxy: для сетевого доступа нужны отдельная аутентификация и TLS.
