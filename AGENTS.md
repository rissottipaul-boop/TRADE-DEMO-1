# Регламент агентов проекта OKX-бота

Общие правила для всех агентов (Copilot-агенты из `.github/agents/`, Claude Code, Codex, Antigravity / Gemini CLI, Meta Muse Code и любые субагенты). Файл агента описывает роль, этот — как работать вместе. Язык ответов и документов — русский.

Проект: полная автоматизация торговли на OKX, сначала demo. План и фазы — [insights/roadmap.md](insights/roadmap.md), текущая работа — [ops/board.md](ops/board.md).

## 1. Команда

| Агент | Роль | Пишет в |
| --- | --- | --- |
| **Project Orchestrator** | Автопилот: ведёт доску, делегирует задачи субагентам, принимает результат | `ops/board.md` |
| **Crypto Insight Hunter** | Исследования: идеи, API, стратегии, проверка фактов | `insights/` |
| **Insight Executor** | Код, тесты, скрипты по задачам с доски | `src/`, `tests/`, `ops/*.ps1`, документация |
| **OKX Trader** | Операции на бирже через `okx` CLI: ордера, grid/DCA-боты, баланс | `insights/` (журналы и отчёты) |
| **Pump Risk Taker** | Рисковый карман: импульсные сделки в пределах `pump-pocket.json` | `insights/pump-*.md`, `data/pump_journal.jsonl` |
| **Ops Sentinel** | Мониторинг движка, риска и ботов; аварийные действия в сторону безопасности | `ops/incidents.md`, `ops/board.md` |

Роли описаны в `.github/agents/*.agent.md`. Для Claude Code те же роли подключены субагентами `.claude/agents/*.md` (`insight-executor`, `crypto-insight-hunter`, `okx-trader`, `ops-sentinel`, `pump-risk-taker`). Это обёртки: субагент читает файл своей роли, поэтому источник правды один. Оркестратор в Claude Code — основная сессия. Antigravity / Gemini CLI читает `.gemini/GEMINI.md` и `AGENTS.md`; Meta Muse Code читает `AGENTS.md` и `.muse/hooks.json`. Codex читает этот `AGENTS.md` и канонический файл выбранной роли, не создавая копий ролей. Общие приоритеты моделей и передача работы — [ops/agent-team.md](ops/agent-team.md), машинный реестр — [ops/agent-routing.json](ops/agent-routing.json). Доска единая; фактическое подключение guard зависит от клиента (§10).

## 2. Автономия: кто что решает

Правило асимметрии: **в сторону безопасности агент действует сам и сразу, в сторону риска — никогда.**

| Решает агент сам, без вопросов | Решает только человек (задача `needs-user`) |
| --- | --- |
| Выбор и порядок задач, декомпозиция, новые задачи на доске | Включение live-торговли (`ops/live-policy.json`) |
| Архитектура, рефакторинг, удаление дублей в коде | Сброс kill-switch и breaker'ов (`python -m src.ops reset …`) |
| Запуск и остановка движка, тестов, demo-экспериментов | Ослабление любого лимита риска (`src/risk.py`, `pump-pocket.json`) |
| Demo-ордера и demo-боты в пределах риск-лимитов | Секреты: `.env`, ключи, токены, профили `okx` CLI |
| Kill-switch, отмена ордеров, остановка ботов при инциденте | Удаление данных и баз состояния |
| Ужесточение лимитов, добавление проверок | Правка guard/автопилота (`ops/hooks/`, `.github/hooks/`, `ops/autopilot.json`) |
| Исследования, документация, статусы инсайтов | Вывод средств — **никогда и никем из агентов** |

Хук `ops/hooks/guard.py` проверяет правую колонку в клиентах, где проверены его подключение и формат вызовов (§10). Наличие файла настроек само по себе этого не доказывает. Во всех клиентах правая колонка обязательна независимо от hook. Отказ guard'а — это граница, а не баг: **не ищи обходной путь** (другая команда с тем же эффектом — нарушение). Запиши задачу `needs-user` с одним конкретным вопросом и переходи к следующей.

Вопросы человеку — только через `needs-user` на доске. Во всём остальном — рекомендуемое действие сразу, а не вопрос «можно?».

## 3. Цикл работы

1. **SYNC** — прочитай `ops/board.md` и материалы задачи. Допускается адресное чтение: `.venv/Scripts/python.exe -m src.agent_context` — обзор, затем та же команда с `--task ID` — полная карточка, зависимости и все активные claims. При ошибке или неоднозначности прочитай исходные строки доски. Это навигация, не разрешение торговли; для торговых и ops-задач — `python -m src.ops status`. Оркестратор ещё переносит на доску новые ответы человека из `notes/decisions/` (§9).
2. **CLAIM** — статус задачи → `in-progress <агент> <ЧЧ:ММ>`, в заметках — файлы, которые будешь менять. Одна задача за раз.
3. **DO** — минимальный законченный инкремент.
4. **VERIFY** — проверь критерий готовности из доски буквально. Нельзя проверить — задача не `done`.
5. **RECORD** — статус `done` + артефакт в заметках; найденные проблемы и идеи → новые строки доски (`ready` или `needs-user`); факты о поведении API → `insights/`.
6. **NEXT** — следующая готовая задача. Останавливайся, только когда готовых нет или всё оставшееся ждёт человека.

Две неудачные попытки подряд → `blocked` с причиной и гипотезой, дальше другая задача. `in-progress` без изменений дольше 3 часов считается брошенным: можно забрать, указав это в заметках.

**Экономия контекста для всех моделей** ([подробности](ops/token-economy.md)):

- Не перечитывай неизменившиеся материалы, уже доступные в текущем контексте; после передачи задачи или изменения файла проверь актуальность.
- Сначала `rg` и релевантные файлы; справочники и skills читай по задаче. Полные критерии готовности и все риск-проверки обязательны.
- Полный лог тестов сохраняй в файл; в контекст выводи команду, код завершения, итог и ошибки. При сбое изучи достаточный участок полного лога.
- Не снижайте назначенные модели, объём проверок или частоту мониторинга ради экономии.
- Повторно используй решения и исследования в Markdown vault Obsidian, проверяя дату, источники и применимость. Состояние торговли получай заново штатными командами; заметки не заменяют сверку с биржей.

## 4. Доска `ops/board.md`

- Колонки: `ID | Задача | Агент | Статус | Зависит от | Критерий готовности | Заметки`. Автопилот читает таблицу машинно — не меняй заголовки.
- Статусы (первое слово ячейки): `ready`, `in-progress`, `blocked`, `needs-user`, `scheduled <ISO-время>`, `done`.
- `scheduled 2026-09-24T10:30+05:00` становится готовой в указанное время. Регулярные проверки после выполнения переставляют себя на следующее время, а не закрываются.
- `needs-user`: в заметках один вопрос, варианты и рекомендация. Работа над остальными задачами продолжается. Ответ человек даёт в чате или файлом `notes/decisions/<ID>.md` (§9).
- Выполненные задачи старше суток переноси в раздел «Архив».

## 5. Параллельная работа

- Перед правкой файла проверь, не менялся ли он за последние 10 минут (`Get-Item <файл> | Select LastWriteTime`). Если менялся — перечитай и правь точечно; не перезаписывай целиком файлы, которые трогал другой агент.
- Claim задачи — это claim её файлов. Файл из чужой активной задачи не трогай: создай задачу-зависимость.
- Не создавай параллельные реализации того, что уже есть (см. §6). Нужен новый модуль — сначала проверь карту.

## 6. Карта кода и команды

Справочник модулей и команд — [ops/code-map.md](ops/code-map.md). Перед изменением модуля прочитай соответствующий раздел карты и исходники.

**Метка владельца ордера (ORDER-OWNER-TAG).** Каждый ордер, algo-ордер и бот, которые ставит агент, получают clOrdId с префиксом владельца. Коды владельцев: OKX Trader `trd`, Pump Risk Taker `pmp`, Ops Sentinel `sen`, Insight Executor `iex`, Crypto Insight Hunter `hnt`.

- ID берётся командой `.venv\Scripts\python.exe -m src.order_owner new <код>`: 32 символа, только буквы и цифры, каждый раз новый.
- Обычный ордер: `okx --demo spot place … --clOrdId <id>`. Так же в `swap`, `futures` и `option place`.
- Algo-ордер: `okx --demo spot algo place … --clOrdId <id>` (CLI отправит его как `algoClOrdId`).
- Бот: `okx --demo bot grid create … --algoClOrdId <id>` и `bot dca create … --algoClOrdId <id>`.

Флага `--tag` у CLI нет: tag всегда `CLI` (у MCP — `MCP`), и по нему владельца не узнать. `--aiBuilderCode` для метки не используйте: он подменяет tag кодом атрибуции OKX. Код проекта ставит префиксы сам. `bot*` — движок и стратегии (реконсилятор считает их своими), `botl*` — только live-runner, `lt`/`rt`/`smk` — тесты. Ордер без clOrdId и tag на demo — это, вероятно, ручной ордер человека: для аудита это info, а не инцидент.

## 7. Готово — значит проверено

- **Код:** все unit-тесты и затронутые самотесты зелёные; поведение на бирже проверено на demo; документация и статус инсайта обновлены.
- **Исследование:** файл в `insights/` со статусом, ключевые факты подтверждены двумя источниками; открытые вопросы стали задачами на доске.
- **Торговая операция:** ID ордера/бота записаны, итоговое состояние проверено повторным запросом, запись в журнале.
- **Инцидент:** причина, принятые меры и что осталось — в `ops/incidents.md`.

## 8. Отчёт в конце хода

Коротко, по делу: **Сделано** (со ссылками на файлы) · **Проверено** (команда и результат) · **Доска** (что изменилось) · **Нужно решение человека** (только если есть `needs-user`).

## 9. Obsidian

Человек открывает репозиторий как vault Obsidian. Пульт — `Home.md`, вьюхи — `notes/views/*.js` (Dataview, только чтение файлов), описание для человека — `notes/Obsidian в проекте.md`.

- **Ссылки** в `insights/`, `ops/` и документации — обычный markdown с относительным путём, как сейчас. `[[вики-ссылки]]` не использовать: их не понимают VS Code, GitHub и разбор доски.
- **`notes/` и `.obsidian/`** — пространство человека. Агенты их не правят; исключение — поле `status` в `notes/decisions/`, см. ниже. Меняешь формат `ops/board.md` или `ops/incidents.md` — поправь разбор в `notes/views/board.js` или `incidents.js`.
- **Ответы на `needs-user`.** Кнопка «Ответить» на пульте создаёт `notes/decisions/<ID>.md` с полями `task`, `date`, `status: новое`. Оркестратор на SYNC читает файлы со `status: новое` и переносит решение в заметки задачи: «Решение человека (`notes/decisions/<ID>.md`): …». Потом меняет статус задачи и ставит в файле `status: перенесено`. Решение из файла не расширяет права: правая колонка §2 остаётся за человеком, guard работает как раньше.

## 10. Мульти-агентная среда (Claude Code + Codex + Google + Muse Code)

Проект использует четыре семейства AI-рантаймов. Роль определяет задачу и права, рантайм — инструменты, модель — исполнителя. При исчерпании лимита сохраняем результат и передаём ту же задачу по правилам ниже. Приоритеты — инженерное назначение, а не доказанный сравнительный рейтинг моделей.

| Рантайм | Модель | Конфиг проекта | Guard-хук | Быстрый старт |
| --- | --- | --- | --- | --- |
| **Claude Code** | `opus`; Sentinel — `sonnet` | `.claude/settings.json`, `.claude/agents/` | PreToolUse настроен; локальные guard-тесты отдельно от проверки клиента | `claude` |
| **Codex** | `gpt-6-astra`; Sentinel — `gpt-6-sol` | `AGENTS.md`, реестр ролей | Автоматический hook проекта ещё не подключён; launcher использует read-only | `ops\agent-rotate.ps1 -Agent codex -Role insight-executor` |
| **Google Gemini CLI / Antigravity** | Gemini CLI `pro`; AGY выбирает модель отдельно | `.gemini/GEMINI.md`, `AGENTS.md` | Найдено несовпадение `PreToolUse` / `BeforeTool`; AGY не проверен | `gemini` или отдельно `agy` |
| **Meta Muse Code** | `muse-spark-1.3` | `.muse/hooks.json`, `AGENTS.md`; загрузка project settings не проверена | Требует проверки trust и Windows/WSL-команды hook | `muse` либо существующий `ops\muse.cmd` |

**Ротация:** `ops\agent-rotate.ps1` без `-Role` сохраняет порядок Claude → Gemini → Muse, Codex добавлен последним; `-Role` применяет приоритеты и модели из реестра. `-Plan` только показывает JSON-план. После запуска процесса скрипт возвращает его код выхода и не повторяет задание другим агентом автоматически. Поддерживает headless-режим:

```powershell
# Автовыбор
ops\agent-rotate.ps1

# Выбор по роли без запуска модели
ops\agent-rotate.ps1 -Role insight-executor -Plan

# После передачи задачи и подтверждения исчерпания лимита Codex
ops\agent-rotate.ps1 -Role insight-executor -SkipAgent codex -TaskId T42 -Plan

# Конкретный агент
ops\agent-rotate.ps1 -Agent muse

# С задачей
ops\agent-rotate.ps1 -Agent antigravity -Prompt "Задача T42: добавь тесты для order_router"

# Headless (без TUI)
ops\agent-rotate.ps1 -Headless -Agent claude -Prompt "Запусти тесты и обнови доску"
```

**Единая точка правды:** `AGENTS.md`, `ops/board.md` и `.github/agents/`. Общий guard не копируем и не ослабляем. В роли Codex по умолчанию выполняет прямую задачу пользователя как Insight Executor; не объявляет себя вторым автопилотом и не перехватывает текущие claims. Запуск через новую ролевую ротацию для непроверенных клиентов ограничен анализом; sandbox Codex не заменяет guard и не гарантирует запрет внешних действий через MCP. Текущие сессии других агентов и их hook/autopilot-настройки не перенастраиваются.

**Передача при лимите:** исходный процесс завершён → заметка задачи содержит роль/рантайм/фактическую модель, изменённые файлы, команды и результаты проверок, незавершённые внешние действия с ID, следующий шаг → задача возвращена в `ready` с пометкой передачи → новый агент делает SYNC и CLAIM. Если процесс оборвался до записи, преемник сначала восстанавливает состояние из diff, доски и журналов; торговые запросы без результата не повторяет, пока не сверит их с биржей. При невозможности сверки — `blocked`. Отказ guard, ошибка авторизации, сети или теста не являются исчерпанием квоты. Переход на другую модель одного провайдера не гарантирует отдельный лимит.

**Установка:**

```powershell
# Gemini CLI (нужен Node.js 20+)
npm install -g @google/gemini-cli

# Meta Muse Code
irm https://dev.meta.ai/install.ps1 | iex

# Первый запуск — авторизация
gemini          # → откроет браузер для входа Google
muse login      # → откроет браузер для входа Meta
```
